# 从 Palantir Ontology 到军工制造试验本体：一条可落地的中国路径

> 本文是给"非本体专家、但懂业务"的读者看的一篇叙事性文档。
> 它一边介绍本仓库（制造业试验数据管理本体 MVP）做了什么，
> 一边穿插讲 Palantir Ontology 的发展与方法论，
> 最后回到一个具体问题：在中国军工制造场景下，本体论到底解决了什么？

---

## 一、先讲一个最朴素的问题

军工制造里最常见的痛苦不是"没有数据"，而是这几句话：

- "这条试验数据为什么判 Fail？谁、用哪一版规格、什么规则判的？"
- "上周规格上限改了，去年那批数据要不要重判？影响哪些批次？"
- "新加一个测量参数，能不能不动数据库表、不停机就上线？"
- "同一个'合格'，工艺、质量、总师办说的是同一件事吗？"

这些问题听起来像 IT 问题，其实是**业务语义问题**。
没有统一的业务语义层，再多的 ERP / MES / QMS / 数据中台，
都只是把同一份混乱在更多系统里复制了一份。

本体论（Ontology）就是被设计来解决这件事的。
本仓库就是把这件事，**在制造业试验场景里做最小可演示的闭环**。

---

## 二、本项目是什么：一句话定位

本仓库 `manufacturing-trial-ontology-mvp` 是一个**最小本体闭环**，证明三件事：

1. **规格变更后，历史结论能否自动重算**
2. **试验过程中，能否动态新增参数而不改数据库表结构**
3. **某条数据为什么 Fail，系统能否给出可审计的推理链**

技术栈非常克制：

- `mvp/ontology/manufacturing-trial.ttl` — 本体定义（TBox）
- Apache Jena Fuseki — 三元组库（ABox、推理结果、规格历史分图存储）
- Owlready2 / Pellet — OWL 推理（保底用确定性 Python 规则）
- FastAPI `/api/v1` — 业务 API
- Streamlit — 演示工作台
- `docs/cq/*` — **CQ（Competency Question）作为业务验收契约**

六个核心对象覆盖了试验数据管理的最小骨架：
`Trial → Batch → Measurement → Parameter / Specification → Result`。

这个 MVP 故意不做"全公司本体""智能制造大脑"。
它要回答的是一件更基本的事：**本体值不值得在你的企业里被认真做一次**。

## 三、Palantir Ontology：一个重新被定义的"本体"

讲到企业级本体，绕不过 Palantir。
但 Palantir 的 Ontology 和大学里讲的 OWL 教材不是一回事。

### 3.1 它把本体重新定义成了"运营层"

传统语义网的本体是**描述性**的：类、属性、关系、公理。
Palantir Ontology 在此之上叠加了**行为层**和**治理层**：

| 层 | 内容 | 类比 |
|---|---|---|
| 语义层 | Object Types / Properties / Link Types / Interfaces | "世界长什么样" |
| 运动层（Kinetic） | Action Types / Functions | "世界怎么被改变" |
| 治理层 | Dynamic Security / Audit | "谁能做什么、留下什么痕迹" |

也就是说，Palantir 不是给你一个 `.ttl` 文件，
而是给你一个**业务对象 + 业务动作 + 权限审计**统一在一起的运行时。
Agent、人、系统调用的不再是表和接口，而是 `Order.expedite()`、`Trial.recompute()` 这种**业务能力**。

### 3.2 没有大模型之前，FDE 是怎么做的

Palantir 真正的"秘密武器"不是平台，是 **FDE（Forward Deployed Engineer）**。
在 LLM 出现之前，FDE 的工作大致是这样：

1. 驻场到客户现场（情报、军工、能源、制药……）
2. 跟一线业务一起把"口头经验、Excel、SOP、老员工脑子里的规则"翻译出来
3. 在 Foundry 里把这些翻译成 Object Types、Action Types、Functions
4. 把散落在 SQL / 代码 / 流程 / 邮件里的规则，**显式挂到本体上**
5. 用 Object Views、Workshop 等给业务做出能用的应用

这套方法的本质是：

> **业务语义不是被写出来的，是被"翻译"出来的。**
> 工程的难度不在 OWL，而在愿不愿意花几个月去搞懂业务。

这也是为什么国内很多"本体项目"做不成——把它当 IT 项目做，
跳过 FDE 这一步，直接交给开发画 ER 图，最终只是一份更花哨的数据字典。

### 3.3 LLM 之后，本体论发生了什么变化

LLM 改变的不是"要不要本体"，而是**本体在 Agent 时代变得更不可或缺**：

- **没有本体的 LLM**：靠 Prompt 拼语义，靠 RAG 拼事实，靠工具拼动作 → 漂移、幻觉、不可解释、不可审计
- **有本体的 LLM**：LLM 只负责"理解意图、规划查询、解释结果"，本体负责"取数、计算、校验、执行"

文档 `12-llm-rigor-and-correctness.md` 里把这件事讲得最干脆：

> **LLM 不是正确性引擎。** 它擅长理解、归纳、解释；
> 它不应该是事实来源、规则执行器、金额计算器、高风险裁决者。

Palantir 在 AIP（AI Platform）里做的事，本质就是把 LLM 钉死在本体上：
Agent 看到的工具是 `get_order_by_id()` 这种**窄而结构化**的本体接口，
而不是裸 SQL；写操作必须走 Action Type，被 SHACL/规则/权限三道闸卡住。

**一句话总结**：
LLM 让本体的价值放大了 10 倍，因为现在终于有人（Agent）真的需要一个稳定可靠的业务语义层来工作了。

## 四、为什么这件事对**中国军工**特别重要

军工制造业有几个其它行业没有的强约束：

1. **极强的可追溯性要求**：每一条结论都要能回溯到"谁、什么版本规格、什么规则、什么证据"。
2. **规格、工艺频繁迭代**：型号在打、试验在跑，规格上下限可能本周就改一次。
3. **多型号、多批次、多参数高度相似但不完全一样**：典型的"重复、类似、多变"。
4. **跨密级、跨单位、跨系统协作**：所长办公室、工艺、质量、总装、外协，各有一套系统。
5. **审查与归档刚性**：每一个 Pass / Fail 都可能在多年后被复查。

把这些约束逐条对照本体论的能力，会发现**本体不是锦上添花，而是缺一不可**：

| 军工痛点 | 没有本体的做法 | 有本体之后 |
|---|---|---|
| 规格变更后历史数据要不要重判 | 改 SQL、跑脚本、出 Excel、邮件确认 | `Specification` 版本化 + `Measurement` 关联 + 自动重推理 + 差异报告 |
| 跨系统的"合格"语义不一致 | 每个系统各自定义状态码 | `Result` 是同一个本体对象，状态语义全企业唯一 |
| 新增测量参数要排期改表 | DBA 排期、停机、回归 | `Parameter` 元数据动态注册，TBox 不动、ABox 直接接收 |
| 事后审计追不到证据 | 翻日志、查代码、问当事人 | `Evidence` 字段 + 推理链落图，SPARQL 一查就到 |
| 总师/工艺/质量"说的不是一件事" | 文档术语表，没人执行 | TBox 是运行时约束，不一致根本写不进去 |
| 多型号试验要复用 80% 的规则 | 每个项目复制一套代码 | `ProcessWindow` / `Rule` 在本体里复用，差异只在实例 |

**从企业视角再退一步**，本体论解决的是这几件"老大难"：

- **降低人员流动的语义损失**：老师傅退休前的经验沉淀到本体，而不是带走。
- **降低型号 N+1 的边际成本**：同类试验的第二个、第三个型号，本体复用率可以做到 70% 以上。
- **降低供应链协同摩擦**：与所内、外协、总装共享的是业务对象，不是各自的字段约定。
- **降低合规与审查成本**：审查给出一条证据链，而不是一堆截图。
- **为 AI 应用打地基**：未来无论谁家大模型，都站在同一套本体之上，不会重做一遍。

这就是这套方法在国内军工真正的"以点扩面"路径——
**先做一个试验场景的最小本体（也就是本仓库），再向工艺、质量、装配、外协逐步扩展。**

## 五、本项目是怎么做的：从语义到验收

### 5.1 七步建模法（来自 `02-modeling-method.md`）

1. 选场景 — 试验数据管理（边界清晰、价值高、上手快）
2. 定边界 — 不做调度、不做生产计划、不做整厂
3. 抽概念 — Trial / Batch / Parameter / Specification / Measurement / Result
4. 画关系 — Batch.has Measurement、Measurement.against Specification、Measurement.yields Result
5. 写规则 — 规格上下限判定、规则版本绑定、推理链字段
6. 填事实 — `demo_data.py` 注入演示数据
7. 做验证 — **CQ 跑通**

### 5.2 关键设计：把"判定"和"推理"拆开

```@E:/company/temp/benti/mvp/core
core/graph.py        — Fuseki 读写、参数注册、推理结果回写
core/inference.py    — 单条判定 + 规格变更后批量重推理 + 差异报告
core/parameters.py   — 参数动态注册与校验
core/qa.py           — 受控问答：SPARQL → 中文解释，不允许 LLM 自己判 Pass/Fail
```

这是有意为之，**严格遵循"LLM 只解释、规则只判定"的分工**：

- 业务结论永远来自确定性 Python 规则（保底）或 Pellet 推理
- LLM 只负责把 evidence 翻译成人话
- 所有结论都带：`rule`、`spec_version`、`deviation`、`reasoner`、`inferred_at`

### 5.3 CQ：把验收变成可执行的契约

`docs/cq/measurement-judgement-cqs.md` 里每一条 CQ 都是一份机器可执行的合同：

| 字段 | 作用 |
|---|---|
| `Business question` | 业务一眼能看懂："M007 为什么 Fail？" |
| `Intent` | 受控意图（如 `why_fail`），约束 LLM 走哪条解释路径 |
| `Demo data` | 准备 fixture，可重放 |
| `SPARQL` | 真正去图里取证据的查询，使用 `{{ontology_graph_iri}}` 等占位符避免硬编码 |
| `Expected` | 期望 row_count、status、rule、spec_version |
| `Evidence fields` | QA 层必须返回的字段集合 |
| `Acceptance` | "SPARQL 返回 1 行 且 QA evidence 包含所有字段" |

一条 CQ 跑通，证明的不只是 SPARQL 能跑，而是：
**fixture → 推理 → 图查询 → QA 解释**这条全链路都没有漂移。

### 5.4 对应到截图里的四阶段方法论

截图里画的是一个推荐的演进节奏，可以这样对回项目：

1. **CQ 工厂** — 业务侧持续提出"必须回答的问题"，沉淀到 `docs/cq/`
2. **骨架提取** — 由 CQ 反推 TBox：哪些对象、关系、规则是必需的，避免本体过度建模
3. **验证闭环** — `tests/test_cq_integration.py` + Fuseki 把 CQ 自动化为回归用例
4. **业务驱动增量扩展** — 每多一个场景（新型号、新参数、新规格），先写 CQ，再扩本体

这条节奏的精髓是一句话：

> **本体不是越大越好，是"能回答的问题越来越多"才好。**

## 六、由浅入深：一个本体演进的"全图"

把全文的脉络压成一张时间轴：

1. **没有本体 / 没有 AI 时代**
   语义沉淀在老师傅脑子、Word、Excel、SOP 里。靠人对齐、靠 SQL 改规则。
2. **有本体 / 没有 AI 时代（FDE 时代）**
   Palantir Foundry / Protégé 把语义、规则、动作显式化。
   人通过 UI 操作业务对象，规则集中、审计可查，但用户面仍是人。
3. **有本体 / 有 AI 时代（AIP / Agent 时代）**
   本体既给人用，也给 Agent 用。
   LLM 在窄工具 + 结构化返回 + 受控写动作的约束下工作，
   严谨场景下做到"决策稳、能解释、可审计"。
4. **本仓库所处阶段**
   验证三个硬命题（规格重判 / 参数动态扩展 / 推理链问答），
   用 CQ 把"业务正确性"变成自动化资产。
5. **下一步（围绕 CQ 的扩展方向）**
   - **CQ 工厂规模化**：从工艺/质量一线收集 CQ，形成 `military-trial-cq-library`
   - **多型号 / 多工艺窗口**：把 `process-window.ttl` 扩展到不同型号、不同试验类型
   - **跨系统对接**：把本体作为 ERP / MES / QMS 的语义中间层（Action Type 化）
   - **Agent 化**：把 `qa.py` 升级为多 Agent 协作（取数 / 校验 / 解释 / 复核），
     所有 Agent 都被钉在本体上，禁止越权
   - **审查与归档**：所有结论默认带证据链落档，满足军工档案要求

## 七、由深入浅：用一句话告诉非技术领导

如果一定要把这件事浓缩到一段话，给型号总师或者所长：

> 我们做的不是又一个数据系统。
> 我们是在试验数据这个最小场景里，
> 把"什么叫合格、谁定的规格、按哪一版判、为什么这么判"
> **变成机器能直接执行、能直接审计、能直接复用的资产**。
> 这件事一旦做成，下一个型号、下一个工艺、下一个所，
> 不再是从 0 开始，而是从这套本体往上长。
> AI 时代真正的护城河不是模型，是这层**业务语义**。
