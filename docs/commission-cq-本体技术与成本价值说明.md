# 委托单 CQ 工程：本体技术与成本价值说明

本文用于技术选型、预算沟通和价值说明。它不承诺固定报价，而是说明为什么本体方案在技术和成本上有优势，以及适合怎么分阶段建设。

## 一句话价值

本体不是为了把系统做复杂，而是为了把业务对象、规则、标准版本、数据结论和影响链统一成可查询、可验证、可复用的语义资产。

## 为什么不用普通表就完了

普通数据库可以存：

```text
委托单表
产品表
试验项目表
任务表
测试数据表
标准表
结果表
```

但普通表通常不直接回答：

- 这个结果为什么是合格？
- 它依据的是哪个标准版本？
- 标准升级后哪些历史结果会翻转？
- 哪些任务因此需要复核？
- 新增一个标准版本后，哪些 CQ 应该重新验证？
- LLM 生成的模型草案是否真的覆盖业务问题？

本体的价值是把这些问题变成可执行关系查询和回归测试。

## 技术优势

### 1. 语义统一

传统系统里，不同模块可能有不同叫法：

```text
委托单 / 申请单 / 检测单
试验项目 / 测试项目 / 大项
测试项 / 指标 / 参数
标准 / 规格 / 阈值
```

本体把这些概念统一成：

```text
CommissionOrder
TestProject
TestTask
TestItem
PassCriterion
StandardVersion
```

好处：

- 跨系统集成时不靠口头解释。
- 字段含义变更时有模型入口。
- 新人、外包、模型、报表都使用同一套语义。

### 2. 关系可追溯

本体不仅存对象，还存关系：

```text
CommissionOrder -> hasTestProject -> TestProject
TestProject -> decomposesToTask -> TestTask
TestItem -> recordsData -> TestDataRecord
TestDataRecord -> hasJudgementResult -> JudgementResult
JudgementResult -> evaluatedAgainstCriterion -> PassCriterion
PassCriterion -> criterionInStandard -> StandardVersion
ReevaluationImpact -> impactsTask -> TestTask
```

好处：

- 能从任务追到数据。
- 能从结果追到标准。
- 能从标准升级追到影响任务。
- 能解释为什么需要复核。

### 3. 标准升级影响分析自动化

传统做法：

1. 发布新标准。
2. 人工查旧标准下的数据。
3. 导出 Excel。
4. 人工重算或写临时脚本。
5. 再人工整理复核任务。

本体方案：

```text
发布 V2
  -> 图谱找到 V1 结果
  -> 规则自动重判
  -> ReevaluationImpact 记录翻转
  -> TestTask 标记 NeedsReview
```

好处：

- 降低漏查风险。
- 结论变化有证据链。
- 复核清单自动生成。

### 4. CQ 让需求可验收

CQ 是 Competency Question，即“本体必须能回答的问题”。

例如：

```text
CQ-CT-004: 标准从 V1 升级到 V2 后，哪些历史结果发生翻转？
```

它不是普通文档，而是配套：

- 业务问题
- 覆盖的类和关系
- 演示数据
- 预期结果
- SPARQL 查询
- Evidence fields

好处：

- 需求不是口头说清楚，而是可执行。
- 模型变更后可以自动回归。
- 评审时能说“这个 CQ 已经通过”，而不是“看起来没问题”。

### 5. LLM 可控接入

本系统支持三种模式：

```text
template_only
llm_with_template_fallback
llm_only
```

关键点：

- LLM 只生成草案。
- 草案保存为 `CQDraft`。
- 草案需要 reviewed。
- LLM 不直接覆盖正式本体。

好处：

- 保留 AI 提效。
- 避免 AI 直接污染正式模型。
- 无网络或无 Key 时仍可用模板演示。

### 6. 工程边界清晰

页面只走 API，不直接调用 core。

```text
Streamlit -> FastAPI -> Core -> RDF/Fuseki
```

好处：

- 页面可以替换。
- API 可以集成其他系统。
- core 可以被测试。
- 本体和数据图可以独立维护。

## 成本优势

### 1. 开源技术栈降低初期采购成本

当前实现主要使用：

- FastAPI
- Streamlit
- Apache Jena Fuseki
- rdflib
- Owlready2 / Pellet
- pytest

这些组件可支持 MVP 和试点阶段，不需要一开始就采购昂贵商业平台。

注意：

> 开源不等于零成本，仍然需要工程建设、部署、运维和人员培训。但它可以显著降低试点阶段的许可成本和供应商锁定风险。

### 2. LLM 成本可控

如果所有建模都调用 LLM，成本和稳定性会受外部接口影响。

本系统的策略：

- 稳定演示用 `template_only`，零 LLM 调用。
- 日常开发用 `llm_with_template_fallback`，失败自动回退。
- 严格测试 LLM 能力时才用 `llm_only`。

好处：

- 演示不受 LLM 费用影响。
- 失败不阻塞流程。
- 能把 token 消耗控制在“草案生成”环节，而不是所有判定环节。

### 3. 减少重复开发成本

传统项目常见重复建设：

- 每个页面各自写业务字段解释。
- 每个报表各自写筛选逻辑。
- 每个接口各自解释标准版本。
- 每次标准升级都写临时脚本。

本体方案把公共语义沉淀到模型里：

- 类复用。
- 关系复用。
- CQ 复用。
- SPARQL 验收复用。
- 标准升级影响分析复用。

长期看，越多系统接入，复用价值越明显。

### 4. 降低人工核查成本

标准升级后，人工核查通常消耗大量时间：

```text
查旧数据 -> 找标准 -> 重算 -> 找翻转 -> 通知复核 -> 留痕
```

本体方案自动输出：

```text
old_status
new_status
flipped
task_status
old_standard
new_standard
```

好处：

- 少导表。
- 少人工比对。
- 少漏项。
- 复核依据更完整。

### 5. 降低沟通成本

本体提供统一语言：

```text
客户讲业务流程
开发看类和关系
测试看 CQ 和 Expected
架构看 TBox/RBox/ABox
运维看 API 和 Fuseki
```

同一个对象在不同角色间保持一致，减少“你说的任务是不是我说的项目”的沟通损耗。

## 价格口径怎么讲

对客户或预算评审不要承诺一个脱离范围的固定总价，建议按建设阶段说明价格构成：

| 阶段 | 主要费用 | 价格解释 |
| --- | --- | --- |
| MVP 演示 | 现有开源组件、本体建模、CQ 梳理、页面演示 | 重点验证“标准升级自动重判”能否跑通，不先购买重型平台 |
| 试点落地 | 数据源对接、权限、审计、更多标准和测试项 | 价格随接入系统数量、标准数量、历史数据规模增加 |
| 生产推广 | 高可用、运维监控、权限体系、变更流程、培训 | 价格主要来自工程化和治理，不是本体文件本身 |
| LLM 增强 | CQ 草案生成、术语归并、变更影响摘要 | 可做成开关；没有 LLM 时模板和人工审核仍能工作 |

可以这样对外表达：

> 这个方案不是先卖一个昂贵平台，而是先用开源技术和小范围本体把关键闭环跑通。真正的价格取决于要接多少业务系统、多少标准、多少历史数据，以及是否需要 LLM 自动生成辅助。这样做的好处是前期投入可控，后续扩展按价值逐步增加。

内部评估时可以把价格拆成四类：

- 一次性建模费用：梳理委托单、产品、试验项目、任务、测试项、标准版本等核心概念。
- 集成费用：连接数据库、API、文件、历史报表。
- 运维费用：Fuseki/服务部署、备份、权限、监控。
- LLM 调用费用：只在生成 CQ 草案、术语建议、影响摘要时发生；核心判定和回归测试不依赖 LLM。

## 和其他方案对比

| 方案 | 优点 | 局限 | 本体方案补足 |
| --- | --- | --- | --- |
| 传统数据库 | 稳定、成熟、性能好 | 语义弱，关系解释靠代码 | 在数据库之上增加语义层 |
| 报表/BI | 展示快 | 难表达规则和因果链 | 本体提供可追溯关系和验证 |
| 规则引擎 | 判定清晰 | 对业务对象语义表达不足 | 本体把规则和对象关系连起来 |
| 纯 LLM | 生成快、交互自然 | 不稳定、不可验证、难审计 | LLM 只生成草案，CQ/SPARQL 验证 |
| 商业知识图谱平台 | 功能全 | 采购和迁移成本高 | 先用开源 MVP 验证价值，再决定是否升级 |

## 适合的建设路径

### 阶段 1：MVP

目标：

- 跑通一个委托单。
- 跑通一个标准升级。
- 跑通 CQ 工程草案。
- 跑通 SPARQL 验收。

当前系统已覆盖。

### 阶段 2：试点

目标：

- 接入更多产品型号。
- 接入更多试验项目。
- 接入真实历史数据。
- 建立标准版本管理流程。
- 形成 CQ 评审制度。

### 阶段 3：生产化

目标：

- 接入权限和审计。
- 接入正式数据库和消息系统。
- 建立本体版本发布流程。
- 接入企业主数据。
- 接入更多标准体系。

## 适合对领导说的版本

> 本体的价值不是多一个技术名词，而是把业务规则和数据关系变成可复用资产。过去标准升级后要人工查历史数据，现在系统能自动重判并给出复核清单。过去模型对不对靠会议讨论，现在 CQ 和 SPARQL 可以自动验收。试点阶段使用开源技术栈，采购成本低；后续如果规模扩大，再考虑商业平台或企业级图数据库。

## 适合对技术负责人说的版本

> 这套架构把本体、规则、CQ、API、页面分层。LLM 只进入 draft，不直接改正式模型；CQ 变成 SPARQL 回归测试；RDF 图保存 ABox 事实和影响链。这样既能快速演示，也能保留工程质量边界。

## 适合对业务负责人说的版本

> 你关心的是：标准变了，哪些历史结果要重看？这个系统能自动找出来，并告诉你为什么。它不是只显示一个“合格/不合格”，而是把实测值、标准版本、阈值、判定结果和复核任务全部串起来。
