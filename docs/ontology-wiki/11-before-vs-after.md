# 11 Before vs After Ontology

## 先看一句话

很多人理解不了本体的价值，不是因为概念太难，而是因为没有把它放进真实工作流里对比。

所以最有效的理解方式不是问：

- “本体是什么”

而是问：

> 在没用本体之前，企业通常怎么做？用了本体以后，究竟改变了什么？

## 先说结论

如果没有本体，企业也不是不能做系统、不能做 AI、不能做流程。

通常还是能做，只是往往靠下面这些方式勉强拼起来：

- 表结构和接口约定
- 术语表和文档
- SQL / 规则引擎
- Workflow
- 人工经验
- Prompt
- RAG

这些东西都能解决一部分问题，但它们通常缺一个共同点：

> 没有把“业务对象、关系、规则、动作”变成统一、可执行、可共享的语义层。

这就是本体真正补的空位。

## 使用本体之前，企业通常是怎么做的

### 方式一：直接围绕数据库表和接口工作

最常见的做法是：

- 系统 A 有一套订单表
- 系统 B 有一套履约表
- 系统 C 有一套客户表
- 各系统之间靠接口和字段映射对接

在这种模式里，真正被共享的通常不是业务对象，而是：

- 表
- 字段
- 状态码
- API 参数

短期能跑，但时间一长就会出现：

- 语义漂移
- 字段同名不同义
- 状态码难统一
- 规则散落在多个系统

### 方式二：靠文档、SOP、术语表维持语义一致

很多企业会补：

- 业务术语表
- 数据字典
- SOP
- 培训材料

这当然有价值，但问题是：

- 文档不是运行时约束
- 术语表不是动作模型
- SOP 不能自动变成 Agent 可调用的规则

结果就是：

- 人看得懂
- 系统不一定用得上
- Agent 更不一定稳得住

### 方式三：把规则写进 SQL、代码和流程

这也是最常见的一条路。

例如：

- SQL 里写一堆 case when
- Java / Python 里写一堆 if else
- 工作流里堆很多条件分支

短期最有效，但长期代价通常是：

- 规则散
- 改规则很贵
- 很难解释“为什么这样判”
- 很难跨系统复用

### 方式四：上 RAG、Prompt、Tool Calling 来补语义

在 AI 项目里，常见补法是：

- 给模型更多文档
- 写更长的 Prompt
- 加更多工具
- 接更多表和接口

它能缓解一部分问题，但仍然有边界：

- 文档不是结构化语义
- Prompt 不是稳定规则
- tool calling 不是业务对象模型

所以你会看到一种常见现象：

- 能回答很多问题
- 但一遇到跨系统业务判断就开始不稳

## 没有本体时，真正的问题出在哪里

很多团队会说自己缺的是：

- 数据整合
- 接口打通
- 提示词优化

这些都可能是真的，但更底层的问题通常是：

## 真问题一：共享的是技术结构，不是业务语义

大家共享的是：

- 表名
- 列名
- 接口字段
- 编码值

而不是：

- 什么是 `Order`
- 什么是 `Shipment`
- 什么是“允许加急”
- 什么动作叫“批准”

## 真问题二：规则存在，但没有被显式管理

企业不是没有规则，而是规则常常存在于：

- 老员工脑子里
- Excel 说明里
- SQL 里
- 前端判断里
- 工作流条件里
- Prompt 里

这意味着规则虽然存在，但并没有成为共享资产。

## 真问题三：系统知道怎么存，业务知道怎么说，Agent 不知道怎么稳地做

这是企业 AI 最常见的断层：

- 数据层知道怎么存事实
- 业务人员知道怎么解释语义
- Agent 能读文档、能调工具

但三者之间没有统一的运行时语义面。

## 使用本体之后，到底变了什么

用了本体以后，最关键的变化不是“图更多了”，而是以下 4 件事发生了。

## 变化一：从“表 / 接口共享”变成“业务对象共享”

之前大家共享的是：

- `ods_order_hdr`
- `shipment_status_code`
- `cust_tier_cd`

之后共享的是：

- `Order`
- `Shipment`
- `Customer`
- `InventoryPosition`

这个变化的价值非常大，因为：

- 业务能看懂
- 开发能围绕它建应用
- Agent 能围绕它调用能力

## 变化二：从“字段更新”变成“业务动作”

之前做写操作时，很多系统实际在做的是：

- 更新一个状态字段
- 调一个写接口
- 触发一个流程节点

但业务上真正发生的是：

- 批准
- 加急
- 升级
- 放行

本体把这些动作显式化之后，系统不再只知道“改了什么”，而是知道“发生了什么业务动作”。

这对：

- 审计
- 权限
- Agent 治理

都非常重要。

## 变化三：从“规则散落”变成“规则可复用”

之前资格判断可能同时出现在：

- SQL
- Java 服务
- 前端页面
- 审批流条件
- Prompt

之后你可以把关键规则提升成：

- 对象关系
- 约束
- 函数
- 动作前置条件

这样最大的变化不是“规则更高级”，而是：

> 规则终于从实现细节里被抽出来，变成了可以复用和治理的资产。

## 变化四：从“AI 读资料”变成“AI 围绕对象和动作工作”

这是本体对 Agent 最直接的价值。

之前 Agent 常常是：

- 读文档
- 猜语义
- 查表
- 调多个工具

之后更理想的状态是：

- 先定位业务对象
- 再沿对象关系获取上下文
- 再调用函数得出判定
- 最后通过受控动作发起变更

这会显著提升：

- 稳定性
- 可解释性
- 可治理性

## 一张明确的前后对比表

| 维度 | 没有本体时通常怎么做 | 有了本体后怎么做 |
|---|---|---|
| 共享对象 | 共享表、字段、API | 共享业务对象、关系、动作 |
| 规则落点 | SQL、代码、流程、Prompt 四处分散 | 显式挂到对象、函数、动作上 |
| 状态语义 | 各系统各自维护状态码 | 用统一业务状态语义对齐 |
| 解释能力 | 靠文档、靠人工解释 | 能回溯到对象、关系、规则、动作 |
| Agent 调用面 | 多工具、多表、多接口拼装 | 围绕对象和动作调用 |
| 写操作治理 | 裸接口、字段更新、局部校验 | 通过受控动作统一约束 |
| 规则变更 | 改多个点，容易漏 | 改共享语义层，复用面更清晰 |
| 复用能力 | 场景复用差 | 对象、关系、动作可跨场景复用 |
| 审计 | 能看到谁改了字段，不一定知道业务含义 | 能看到执行了什么业务动作 |
| 团队协作 | 技术和业务经常各说各话 | 更容易围绕同一语义面对齐 |

## 本体的真实价值点到底是什么

如果你只想知道“它究竟值在哪”，我建议只看下面这 6 条。

## 价值一：把隐性语义变成显性资产

这是最大的价值，也是最容易被低估的价值。

在没做本体之前，企业当然有业务语义。

只是这些语义分散在：

- 人
- 文档
- 表
- 代码
- 流程

做了本体之后，它第一次被提取成共享资产。

## 价值二：让决策依据稳定下来

很多企业系统不是没规则，而是规则很难保持一致。

本体的价值在于：

- 把对象和关系固定下来
- 把规则挂在稳定对象上
- 把动作挂到受控语义上

于是“同一个问题”在不同系统、不同 Agent、不同应用里更容易得到一致判断。

## 价值三：让解释不再只是事后补文案

没有本体时，很多“解释”只是：

- 把 SQL 结果翻译成人话
- 把 Prompt 思路包装成自然语言

有了本体以后，解释更接近：

- 涉及哪些对象
- 对象之间有什么关系
- 命中了哪些规则
- 最终触发了什么动作

这才更接近真正的可解释。

## 价值四：让 Agent 更容易被管住

很多团队以为本体的价值是“让 Agent 更聪明”。

这只说对了一半。

它更重要的价值其实是：

> 让 Agent 不只是更聪明，而是更容易被约束在正确的业务对象和动作边界里。

这比“回答更炫”重要得多。

## 价值五：让跨系统业务协同变简单

当一个业务判断跨：

- ERP
- CRM
- WMS
- 数仓

时，最大的难点往往不是 API 调不通，而是：

- 这些系统里的对象并没有天然对齐
- 这些系统里的状态也没有天然对齐

本体的价值，就是把这个“对齐层”建立起来。

## 价值六：让变化成本下降

规则真正难的不是写出来，而是后续不停变化。

当规则散在很多地方时，每次变更都很痛。

当它们被提升到对象、关系、函数、动作层时，变化至少会变得：

- 更容易定位
- 更容易解释
- 更容易复用

## 什么不是本体的真实价值

这也很重要，因为很多项目会被错误期待拖死。

### 不是“把所有知识都装进图里”

这太大，也通常不必要。

### 不是“自动替你解决所有数据质量问题”

数据质量、元数据治理、主数据治理依然重要。

### 不是“只要建了图，Agent 就一定变聪明”

如果对象、关系、规则建得不好，Agent 还是会错。

### 不是“可以替代 DDD、元数据管理、Workflow”

它是补层，不是替代层。

## 什么时候你会真正感受到价值

通常在下面这些时刻，价值最明显：

### 场景一：同一个业务词在多个系统里意思不一致

例如“有效订单”“可发货订单”“加急订单”。

### 场景二：同一个判断规则散在很多地方

例如：

- SQL 里一套
- 审批流里一套
- 人工 SOP 里一套

### 场景三：Agent 明明能拿到数据，但还是经常判断不稳

这往往说明缺的不是更多数据，而是共享语义和动作边界。

### 场景四：业务要求“给结论，也给依据”

这时候本体价值会非常直接。

## 一个最朴素的判断标准

如果你问：

> 本体真实价值到底是什么？

我会给一个很朴素的答案：

> 它不是让企业“知道得更多”，而是让企业“围绕同一业务语义更稳定地判断、协作、执行和审计”。

这才是它最硬的价值。

## 什么时候不值得做

如果你的场景满足下面这些情况，本体价值通常没那么大：

- 单系统单表就能解决
- 规则非常简单
- 没有跨系统语义冲突
- 不需要解释和审计
- 不需要 Agent / 多应用围绕统一对象工作

这时上本体，收益可能覆盖不了成本。

## 这一页应该记住什么

只记住 5 句：

1. 没有本体时，企业也能做系统，但通常靠表、接口、文档、SQL、Workflow、Prompt 拼接语义。
2. 本体补的不是“有没有数据”，而是“有没有统一、可执行、可共享的业务语义层”。
3. 本体最真实的价值，不是图更漂亮，而是决策更稳、解释更强、治理更清楚。
4. 对 Agent 来说，本体最大的增量是把对象、关系、规则、动作变成稳定调用面。
5. 如果场景本来就很简单，本体不一定值得做。
