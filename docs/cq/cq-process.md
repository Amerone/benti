# CQ 工程流程规范

本项目采用轻量版 SAMOD/XD 流程：用业务故事驱动小步本体增量，用 CQ 固化需求，用 SPARQL/SHACL/pytest 做可重复验收。

## 1. Story

每次只选择一个业务故事或一个内聚故事集。故事必须说明：

- 业务触发场景；
- 涉及的对象、关系、状态；
- 用户或系统需要得到的答案；
- 用于验收的演示数据。

委托单试验示例：`CO-2024-001` 分解为试验项目、试验任务、试验数据、判定结果和标准升级影响。

## 2. CQ

每个故事派生一个或多个 CQ。CQ 是自然语言问题，但必须能落到可执行验证。

每条 CQ 至少包含：

- `Business question`：业务问题；
- `Intent`：稳定意图名；
- `Source`：来源；
- `Covers`：覆盖的类、关系或规则；
- `Demo data`：验收样例；
- `Expected`：结果断言；
- `Evidence fields`：返回证据字段；
- `Generated by`：生成来源；
- `Human review status`：人工复核状态；
- `Acceptance`：通过条件；
- 一个 `sparql` 代码块。

## 3. Context

上下文声明用于把自然语言问题转成可检查事实：

- 对象必须有稳定业务 ID，例如 `orderNo`、`localId`；
- 关系必须能从图中追溯，例如 `hasTestProject`、`decomposesToTask`；
- 状态必须显式落图，例如 `taskStatus`、`resultStatus`；
- 推理或重判结果必须保留旧值、新值和影响对象。

## 4. Formalization

CQ 验收分两层：

- **SPARQL** 验证“能否回答业务问题”，由 CQ 文档中的查询和 `Expected` 字段驱动；
- **SHACL** 验证“图结构是否满足最低形状约束”，由 `mvp/shapes/commission-testing-shacl.ttl` 驱动。

SPARQL 适合验证答案、证据字段和推理结果；SHACL 适合验证必填属性、关系完整性、数据类型和结构约束。

## 5. Unit Gate

本地单元门禁：

```powershell
python -m pytest tests/test_cq_workflow.py tests/test_commission_cq_engine.py -q
```

覆盖内容：

- CQ Markdown 解析；
- `Expected` 断言；
- SHACL shape conform/non-conform；
- draft payload 可发布性。

## 6. Release Gate

发布 CQ draft 前必须通过 `validate_draft_quality_gate`：

1. 至少包含一个 candidate CQ；
2. 至少包含一个 SPARQL test；
3. `draft_turtle` 必须是合法 Turtle；
4. `draft_turtle` 必须通过委托单 SHACL shapes；
5. release manifest 必须记录 `quality_gate` 证据。

API 发布失败时返回 `CQ_ENGINE_ERROR`，draft 状态保持 `reviewed`，不会写入有效 release。

## 7. Publication

发布产物写入 `runtime/cq-releases/<ontology-id>/<release-id>/`：

- `draft.ttl`
- `candidate-rules.json`
- `sparql-tests.json`
- `manifest.json`

`manifest.json` 中的 `quality_gate` 是该版本 CQ 工程质量证据。
