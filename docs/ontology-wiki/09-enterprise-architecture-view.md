# 09 Enterprise Architecture View

## 先看一句话

如果把企业里的 DDD、元数据管理、Ontology、Workflow、Agent 放到同一张图里，更合理的理解通常不是“谁替代谁”，而是：

> DDD 管系统内部的业务边界，元数据管理管数据资产治理，Ontology 管跨系统业务对象与动作语义，Workflow 管执行路径，Agent 管交互、解释与协调。

这五层一起工作，企业 AI 才容易稳定。

## 一张分层图

可以先把整套架构压成下面这张文字图：

```text
用户 / 操作员 / 分析师 / 管理者
            │
            ▼
Agent / Copilot / Chat / App UI
            │
            ▼
Workflow / Approval / Orchestration
            │
            ▼
Ontology / Operational Semantics / Actions / Functions
            │
     ┌──────┴──────┐
     ▼             ▼
DDD-aligned Systems   Metadata Management / Catalog / Lineage / Glossary
     │             │
     └──────┬──────┘
            ▼
ERP / CRM / MES / WMS / Data Lake / APIs / Documents / Events
```

这张图里有一个关键点：

- Ontology 不替代底层业务系统
- Ontology 也不替代元数据平台
- Agent 更不应该直接跨过中间层去裸连所有系统

## 每一层各自负责什么

### 1. 源系统层

这是事实和操作的来源。

通常包括：

- ERP
- CRM
- MES
- WMS
- 工单系统
- 数据湖 / 数仓
- 外部 API
- 事件流
- 文档系统

这一层回答的是：

- 事实从哪里来
- 写操作最终回到哪里

### 2. DDD 对齐的业务系统层

这是应用设计层。

它的职责是：

- 用限界上下文控制业务边界
- 用聚合与领域规则保证局部一致性
- 把通用语言落进代码和服务接口

这一层回答的是：

- 每个系统内部怎么建模才不乱
- 某个业务能力归谁负责

它不负责：

- 提供全企业统一对象搜索入口
- 直接承载跨系统共享动作语义

### 3. 元数据管理层

这是数据治理层。

它的职责是：

- 发现资产
- 维护目录
- 展示血缘
- 管分类分级
- 管 glossary
- 管质量与责任归属

这一层回答的是：

- 有哪些数据资产
- 这些资产是否可信
- 谁负责
- 从哪来，流到哪去

它不擅长：

- 定义业务对象级动作
- 直接让 Agent 围绕动作与对象工作

### 4. Ontology 层

这是跨系统业务语义层，也是最容易被误解的一层。

它的职责是：

- 定义业务对象
- 定义对象关系
- 统一关键状态语义
- 显式化规则与资格判定
- 提供受控业务动作
- 暴露给应用、人和 Agent 使用

如果放到 Palantir 语境里，对应的是：

- object types
- link types
- interfaces
- action types
- functions
- object views / object explorer / OSDK

这一层回答的是：

- 对企业来说“订单”“资产”“告警”“客户”到底是什么
- 这些对象之间如何连接
- 哪些动作可以对这些对象执行

### 5. Workflow 层

这是高风险执行路径层。

它的职责是：

- 固定流程顺序
- 定义审批节点
- 接住人工确认
- 协调外部写操作

这一层回答的是：

- 什么顺序执行
- 哪些节点必须审批
- 哪些写操作必须走受控流程

如果没有这层，Agent 容易“语义对了，但动作失控”。

### 6. Agent / 应用层

这是用户真正接触到的入口层。

它的职责是：

- 理解用户意图
- 调用对象和函数
- 解释结果
- 发起动作
- 在流程中协助收集参数

它最不应该做的是：

- 自己发明业务语义
- 自己判断所有关键状态迁移
- 直接裸写多个底层系统

## 为什么这套分层更稳

### 好处一：职责不再互相污染

最常见的问题不是某一层太弱，而是所有层都在偷偷做别人的事。

比如：

- 让元数据平台承担业务动作层
- 让 Agent 承担领域规则层
- 让 Workflow 承担本体建模层
- 让 DDD 承担全企业统一语义目录

结果就是每一层都很累，而且都做不好。

### 好处二：Agent 不再直接面对原始复杂性

Agent 不需要直接理解：

- 10 个系统的表结构
- 20 种状态码
- 30 个写接口

它只需要围绕：

- 对象
- 关系
- 函数
- 动作

工作。

### 好处三：治理和执行可以同时成立

很多团队的问题是二选一：

- 要么快，但不可控
- 要么可控，但很难用

当 Ontology + Workflow 组合起来时，通常能同时拿到：

- 语义清晰
- 动作受控
- 结果可审计

## 一个试点落地视图

如果你要从零做试点，建议按下面顺序铺层，而不是一次性全做。

### 阶段一：先选业务场景

优先选：

- 高风险判断
- 跨系统语义冲突明显
- 结果需要解释

例如：

- 发货资格
- 异常升级
- 检修放行
- 特殊审批

### 阶段二：梳理 DDD 边界

先确认：

- 这个场景跨了哪些业务上下文
- 哪些规则属于哪个系统内部
- 哪些概念不能强行合并

这一步是为了防止你在 Ontology 层做出“伪统一”。

### 阶段三：补元数据治理最小闭环

至少补齐：

- 关键表/事件/接口的来源
- 关键字段定义
- 关键血缘
- 数据责任人

否则后面建出来的对象会失真。

### 阶段四：建立最小 Ontology

只做最少对象：

- 3 到 5 个 object types
- 关键 link types
- 1 到 3 个 action types
- 1 到 2 个 functions

目标不是完整，而是能支持一个业务闭环。

### 阶段五：接 Workflow

把：

- 审批
- 人工确认
- 外部写回
- 通知

接进流程。

### 阶段六：再让 Agent 接进来

Agent 先做：

- 查询
- 解释
- 参数收集
- 动作发起

关键写操作仍然走 action + workflow。

## 一个会议里能讲清的分工版本

如果你要对齐架构、数据、AI 三拨人，可以直接用下面这版分工：

- 架构团队：负责 DDD 边界、服务责任和系统内规则
- 数据治理团队：负责 metadata、glossary、lineage、quality
- 业务建模团队：负责 ontology 对象、关系、状态、动作
- 平台团队：负责 workflow、权限、审计、集成
- AI / 应用团队：负责 agent、copilot、UI、交互编排

这能避免大家反复争论“这个到底算不算谁的活”。

## Palantir 风格落地时怎么套这张图

如果采用 Palantir 路线，这张图可以进一步具体化：

- DDD-aligned systems：原有业务系统和各自上下文
- Metadata management：Purview / OpenMetadata / DataHub 一类平台
- Ontology：Foundry Ontology
- Workflow / controlled execution：Action Types + 平台内流程/审批能力
- Agent / apps：AIP、Workshop、OSDK 应用、对象视图

这样你就不会把 Palantir Ontology 误当成：

- DDD 的替身
- 或者 metadata catalog 的替身

## 最容易出现的架构误区

### 误区一：试图先做企业总本体

这通常会过早抽象，最后只剩术语表。

### 误区二：没有 DDD 边界就做统一对象

最后常常会把不该统一的概念硬压成一个对象。

### 误区三：只有数据目录，没有动作语义

这会让 Agent 只能“看”，很难“稳地做”。

### 误区四：让 Agent 越过 action / workflow 直连写接口

短期很快，长期很难审计，也很难治理。

## 这一页应该记住什么

只记住 5 句：

1. DDD、元数据管理、Ontology、Workflow、Agent 最好分层协作。
2. Ontology 在中间层，负责把跨系统业务对象和动作变成统一语义面。
3. Workflow 负责兜住高风险执行路径。
4. Agent 最适合站在 Ontology 和 Workflow 之上，而不是直接站在底层系统之上。
5. 真正稳的企业 AI，不是某一层特别强，而是层与层之间边界清楚。
