# 委托单 CQ 工程客户演示讲稿

这份文档给演示人使用。目标不是把技术讲复杂，而是让客户理解：本体能让业务对象、规则、标准版本和历史数据影响链变得可追溯、可验证、可扩展。

## 演示总目标

让客户在 10 分钟内看懂三件事：

1. 系统能把委托单自动拆成试验任务。
2. 系统能按标准自动判定测试结果。
3. 标准升级后，系统能自动找出历史结论翻转，并标记复核任务。

## 演示前准备

确认两个地址可用：

```text
API: http://127.0.0.1:8000/api/v1/health
页面: http://127.0.0.1:8501
```

如果用备用端口：

```text
API: http://127.0.0.1:8010/api/v1/health
页面: http://127.0.0.1:8502
```

## 1 分钟开场

可以照读：

> 今天演示的不是一个普通报表系统，而是一个以“本体”为底座的试验业务模型。它把委托单、产品、试验项目、测试任务、测试项、实测数据、判定结果和标准版本都建成可查询、可追溯的语义关系。这样一来，系统不仅知道结果是什么，还知道结果为什么产生、依据哪个标准、标准变化后哪些历史数据会受影响。

## 第 1 步：进入客户演示页

点击顶部：

```text
委托单试验
```

讲解词：

> 这个页面面向业务客户，不要求客户理解 OWL、RDF 或 SPARQL，只展示他们关心的完整业务链路。

## 第 2 步：初始化委托单

点击：

```text
初始化 / 重置 CO-2024-001
```

客户应该看到：

- 委托单：`CO-2024-001`
- 委托人：李工
- 产品：相控阵雷达导引头
- 型号：`X-01`
- 项目 1：高低温振动试验
- 项目 2：电磁兼容试验

讲解词：

> 这里系统已经把一张委托单变成了结构化业务图谱。委托单关联产品，委托单包含试验项目，试验项目再分解成试验任务。这个关系不是写死在页面里的，而是在本体和数据图里维护。

## 第 3 步：讲任务自动分解

指出页面中的任务：

```text
P-001 -> T-001
P-002 -> T-002
```

讲解词：

> 当前规则是“一个试验项目生成一个试验任务”。这条规则不是散落在代码里的业务习惯，而是可以被 CQ、规则文件和本体关系共同约束。后续如果变成“一个项目拆多个任务”，模型也有清晰扩展点。

## 第 4 步：讲测试项和判定

指出测试项：

```text
T-001 / RCS_MEAN / 0.042 / V1 / Pass
T-002 / BER / 0.00021 / V1 / Pass
```

讲解词：

> 系统不是只保存“合格”两个字，而是保存实测值、单位、通过条件、标准版本、判定结果和判定原因。因此结果可解释，也可以在标准变化后重新计算。

## 第 5 步：触发标准升级

点击：

```text
触发标准升级 V2
```

客户应该看到：

```text
RCS_MEAN: Pass -> Fail
T-001: NeedsReview
BER: Pass -> Pass
T-002: Completed
```

讲解词：

> 三个月后标准升级，RCS 阈值从 0.05 收紧到 0.035。传统系统通常要人工查历史记录，甚至要导 Excel。这里系统自动找到旧标准下判过的数据，用新标准重算，并把结论翻转的任务标记为 NeedsReview。

## 第 6 步：强调本体优点

可以分四句话讲：

1. > 本体让业务对象有统一名字，不同系统说的“委托单、任务、测试项、标准版本”能对齐。
2. > 本体让关系可查询，不只是查表，而是查“这个结论受哪个标准影响”。
3. > 本体让规则可追溯，判定结果可以回到实测值、阈值和标准版本。
4. > 本体让变更可回归，标准升级后可以自动重判历史数据。

## 第 7 步：客户常问问题回答

### 问：这和普通数据库有什么区别？

答：

> 数据库擅长存数据，本体擅长表达“这些数据是什么意思、彼此是什么关系、规则依据是什么”。这个系统底层仍然可以接数据库，但在数据库上面多了一层可解释的业务语义模型。

### 问：这是不是只能做演示？

答：

> 不是。当前 demo 已经把 CQ、SPARQL、规则、API、页面和自动化测试串起来。它的价值不在于页面多复杂，而在于业务模型可以被验证、可以回归、可以扩展。

### 问：标准升级为什么要用本体？

答：

> 因为标准版本、通过条件、判定结果、历史数据之间是关系网络。用本体建模后，系统能知道哪些数据受哪个标准影响，而不是只靠人工记忆或报表字段。

### 问：LLM 会不会乱改模型？

答：

> 不会。这里 LLM 只生成草案，不直接覆盖正式本体。草案需要 reviewed，需要 CQ 和 SPARQL 验证后才进入正式模型。

## 10 分钟演示节奏

| 时间 | 操作 | 讲解重点 |
| --- | --- | --- |
| 0-1 分钟 | 开场 | 本体不是报表，是业务语义模型 |
| 1-2 分钟 | 进入委托单试验页 | 客户只看业务流程，不看技术细节 |
| 2-3 分钟 | 初始化 CO-2024-001 | 委托单、产品、项目、任务变成关系图 |
| 3-5 分钟 | 查看测试项和 V1 判定 | 实测值、阈值、标准、结果可追溯 |
| 5-7 分钟 | 触发 V2 标准升级 | 自动重判历史数据，发现结论翻转 |
| 7-9 分钟 | 解释 NeedsReview | 系统自动形成复核清单 |
| 9-10 分钟 | 总结 | 可追溯、可验证、可扩展、可回归 |

## 演示结束总结

可以照读：

> 这套系统的核心价值，是把业务规则、标准版本和数据结论放到同一个语义模型里。客户看到的是一个普通流程页面，但后台已经具备本体建模、规则判定、标准升级影响分析和 CQ 回归验证能力。后续接入更多产品、更多试验项目、更多标准版本时，不是重新堆页面，而是在同一个本体框架下扩展。
