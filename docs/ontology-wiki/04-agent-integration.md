# 04 Agent Integration

## 快速结论

本体不是用来替代这些东西的：

- RAG
- Skills
- Workflow
- Tool calling

它更适合作为这些东西的下层语义底座。

## 一张简单分工表

| 能力 | 更擅长解决什么 |
|---|---|
| RAG | 把相关文档和上下文拿给模型 |
| Skills | 约束任务步骤、沉淀提示经验 |
| Workflow | 固定高风险流程和执行路径 |
| Tools | 获取实时数据、执行动作 |
| 本体 | 统一业务语义、表达规则、支撑推理与解释 |

## 展开理解

### 为什么只靠 RAG 不够

RAG 能把文档找回来，但文档不等于结构化规则。

问题在于：

- 文档可能互相冲突
- 文档可能版本过时
- 文档中的规则可能没有形式化
- 模型读到了，不代表理解正确

### 为什么只靠 Skills 不够

Skills 擅长把经验变成可复用操作说明。

但 Skills 的边界在于：

- 更像行为提示，不是语义约束
- 场景一多就容易碎片化
- 规则一变，维护成本会上升

### 为什么只靠 Workflow 不够

Workflow 可以把高风险路径固定下来。

但如果流程中的判断节点仍依赖 LLM 去“理解业务状态”，语义错位还是会发生。

如果你把所有规则都硬编码进流程，又会进入另一种问题：

- 规则爆炸
- 维护困难
- 没人敢改

## 更合理的组合方式

### 推荐架构

1. 用本体定义：
   - 核心概念
   - 关系
   - 约束
   - 可推理的判定条件

2. 用工具获取：
   - ERP / MES / CRM / 工单系统中的实时事实

3. 用 RAG 补充：
   - 说明文档
   - SOP
   - 合同条款
   - 非结构化上下文

4. 用 Workflow 控制：
   - 高风险动作
   - 人工审批
   - 外部系统写操作

5. 用 LLM 负责：
   - 解释
   - 归纳
   - 交互
   - 多步任务协调

### 一句更实用的话

> 本体负责“判断依据”，Workflow 负责“执行路径”，RAG 负责“补充上下文”，LLM 负责“表达和协调”。

## 深入一点

### 一个推荐的落地顺序

不要先问“怎么做企业总本体”，先按下面顺序走：

1. 选一个高风险判断场景  
   比如发货资格、赔付资格、审批路径

2. 把核心概念和规则抽出来  
   不追求全，只追求关键判断正确

3. 让 Agent 先在“读”和“解释”层用起来  
   先别直接给写权限

4. 把推理结果接入 Workflow  
   让流程基于语义判断而不是纯文本判断

5. 再逐步扩到更多场景  
   比如库存、合同、质检、售后

### 判断是否值得上本体

满足下面 3 条以上，通常就值得：

- 多系统语义经常冲突
- 规则经常变
- 决策需要解释
- 结果要审计
- 多 Agent / 多团队需要共享语义
- 仅靠 Prompt 调不稳

## Palantir 风格集成怎么看

如果把 Agent 集成放到 Palantir 的产品语境里，可以把职责再说得更具体一点：

- Ontology object types：提供 Agent 可理解的业务对象
- link types / interfaces：提供跨对象、跨类型的稳定语义面
- functions：提供可复用的业务判定逻辑
- action types：提供受控写操作入口
- Object Views / Object Explorer：提供人机共用的对象上下文入口
- OSDK：提供程序化调用面

这种做法的一个重要价值是：

> Agent 不需要直接理解底层系统的几十种表结构和写接口，而是围绕统一业务对象和动作工作。

这正是企业 Agent 稳定性会明显提升的地方。
