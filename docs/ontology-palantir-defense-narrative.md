# 从制造业试验本体 MVP 到军工企业本体化运营

本文试图回答一个具体问题：为什么一个看起来很小的“制造业试验数据管理本体 MVP”，可以用来说明 Palantir Ontology 一类方法在军工领域的价值。

结论先说清楚：本项目不是在做一个“会聊天的试验系统”，也不是在做一个大而全的知识图谱平台。它真正验证的是一条更底层的路线：

> 把试验业务里的对象、参数、规格、规则、判定结果和证据链变成可执行、可校验、可追溯的语义资产。

军工领域的很多问题并不来自“没有系统”，而是来自系统太多、型号太多、版本太多、规则太多、文档太多。不同项目、不同批次、不同分系统之间的需求高度相似，却又总有局部变化。没有本体时，这些变化常常散落在 Word、Excel、PDM/PLM、MES、QMS、试验台账、审批流程和专家经验里。用了本体以后，变化不会消失，但变化可以被命名、定位、验证、重算和审计。

## 1. 先从本项目讲起

本项目的业务对象很少，但闭环完整：

| 本体对象 | 本项目含义 | 军工企业里的对应类比 |
| --- | --- | --- |
| `Trial` | 一次试验 | 型号试验、工艺验证、鉴定试验、例行试验 |
| `Batch` | 试验批次 | 批产批次、试制批次、状态件批次 |
| `Parameter` | 被测参数 | 温度、压力、尺寸、振动、频率、力矩、材料指标 |
| `Specification` | 规格版本 | 技术条件、验收准则、工艺窗口、检验规范版本 |
| `Measurement` | 实测记录 | 试验台采集值、检验记录、过程参数 |
| `Result` | 判定结果 | 合格、不合格、超上限、低于下限、需复核 |

当前系统把数据分为四类 named graph：

- `ontology graph`：类、关系、属性、约束等定义。
- `data graph`：试验、批次、参数、测量等业务事实。
- `spec graph`：规格版本和变更历史。
- `result graph`：判定结果、规则名、规格版本、偏差、证据链。

这个拆分很关键。军工企业最怕的不是数据量大，而是“结论没有来路”。某个试验项为什么不合格、依据哪个版本的规范、当时上下限是多少、后来规范变更后历史结论是否要重判，这些问题不能靠口头解释，必须让系统能复现。

本项目已经验证了三个最小命题：

1. 规格变更后，历史测量可以重推理，并输出哪些结论发生变化。
2. 新参数可以运行时注册，不必每次都改数据库表结构。
3. `M007 为什么 Fail？` 这类问题可以通过结构化 evidence 回答，而不是让大模型凭感觉解释。

这里最重要的设计选择是：最终业务判定由 `mvp/core/inference.py` 中的确定性规则执行。规则非常朴素：

```text
value < lower -> Fail_Low
value > upper -> Fail_High
otherwise     -> Pass
```

朴素不是缺点。对军工、质量、试验、合规这类场景，第一阶段最需要的不是“复杂”，而是稳定、可解释、可重放。LLM 在本项目里只做意图识别和解释，不直接决定 `Pass` 或 `Fail`。这正是高严谨场景里本体和 AI 的正确分工。

## 2. Palantir Ontology 给我们的参照

Palantir 官方把 Ontology 放在其架构核心位置，并强调它表示的是企业复杂、互联的“决策”，而不只是数据。它把数据源统一为对象、属性、链接，又把动作、逻辑和安全治理放进同一个运营层。

用更工程化的话说，Palantir Ontology 不只是一个 OWL 文件，也不只是图数据库。它更像：

> 面向运营的对象层 + 关系层 + 行为层 + 规则层 + 安全治理层。

Palantir 的几个关键积木可以这样理解：

| Palantir 概念 | 含义 | 本项目类比 |
| --- | --- | --- |
| Object Type | 现实实体或事件的类型 | `Trial`、`Batch`、`Measurement` |
| Object | 类型的实例 | `T001`、`B03`、`M007` |
| Property | 对象属性 | 测量值、单位、规格版本、偏差 |
| Link Type | 对象之间的关系 | `Batch -> Measurement`、`Measurement -> Result` |
| Action Type | 有业务意义的一次变更 | 录入测量、变更规格、触发重判 |
| Function | 可复用业务逻辑 | 测量判定、规格变更影响分析 |
| Security / Governance | 谁能看、谁能改、谁能执行动作 | 军工环境里的密级、型号权限、岗位授权、审计 |

Palantir 在军事语境里的说法也很值得借鉴：本体可以统一前方部署力量的战备信息和支撑侦察、目标选择的运营流程，为多国团队提供共享的 operational world。这个表述不应该被简单照搬成国内项目口号，但它揭示了方法论核心：不是把所有表汇总到一起，而是把不同角色共同决策所需的对象、关系、规则和动作统一起来。

对军工企业来说，类似问题并不遥远。一个型号从论证、设计、试制、试验、定型到批产，涉及设计、工艺、质量、供应链、试验、生产、售后和保密多个条线。每个条线都有自己的系统和术语。如果缺少统一本体，系统之间只能共享字段，不能共享语义；只能传递结果，不能解释依据；只能做流程审批，不能稳定复用规则。

## 3. 为什么军工需求特别适合从本体切入

军工领域的需求有三个典型特点：重复、类似、多变。

重复，是因为不同型号都会遇到需求分解、设计更改、工艺验证、试验鉴定、质量放行、偏差处理、供应商协同等流程。

类似，是因为流程结构相似，但对象、参数、指标、规范、密级、责任主体和验收准则不同。

多变，是因为型号状态、技术条件、试验大纲、工艺窗口、供应替代、合规要求都会变，而且变更必须保留痕迹。

传统系统通常会用以下方式应对：

- 为每个型号、每类试验、每个部门建局部表单。
- 通过数据字典和接口文档约定字段含义。
- 把规则写进代码、SQL、流程条件或 Excel。
- 由专家人工解释异常、判断影响范围。
- 新需求来了就复制旧页面、改字段、改接口、再上线。

这些方式短期有效，但长期会形成技术债和语义债。最常见的结果是：同一个“合格判定”在多个系统里口径不同；同一个“批次”在生产、试验、质量系统里不是同一个对象；同一个“规格版本”在文档里有，在判定结果里却没有结构化记录。

本体可以解决的不是“让需求不变化”，而是让变化变得可管理：

| 军工企业问题 | 本体化解法 |
| --- | --- |
| 同类需求反复做 | 抽出稳定对象、关系、动作和 CQ 模板，复用到不同型号 |
| 字段同名不同义 | 用统一术语、属性定义、单位和来源约束消除歧义 |
| 规格变更影响不清 | 规格版本化，历史数据可重算，可输出影响清单 |
| 试验结论不可解释 | 保存规则、版本、上下限、偏差、时间和来源证据 |
| 规则散落在代码和文档里 | 将关键规则提升为可管理的函数、约束或判定服务 |
| 专家经验难沉淀 | 用 CQ、规则和本体变更记录沉淀为组织资产 |
| AI 回答像真的但不可审计 | AI 只解释结构化 evidence，事实和规则由系统提供 |

从企业角度看，这套方法的价值不是“多一个知识图谱”，而是建立一层可复用的业务准确性基础设施。

## 4. 没有 AI 模型之前，本体论是怎么做的

在没有大模型之前，本体工程主要靠人，尤其靠领域专家、知识工程师、软件工程师一起工作。Palantir 的 Forward Deployed Engineering 可以看作一种非常工程化的代表：工程师深入客户现场，贴近真实问题，把现场反馈和核心工程团队连接起来，快速把需求、数据、应用和平台能力迭代成可用系统。

这个过程通常是这样的：

1. 现场访谈：和工艺、质量、试验、设计、生产等角色一起梳理真实问题。
2. 提取 CQ：把“系统必须能回答什么问题”写成自然语言问题。
3. 抽对象：识别稳定业务对象，例如试验、批次、参数、规格、结果。
4. 抽关系：确定对象如何连接，例如批次包含测量，测量对应参数和结果。
5. 抽规则：明确上下限、版本、资格、约束、状态转移。
6. 建 TBox：定义类、属性、关系和约束。
7. 建 ABox：把真实业务实例接入图谱或对象层。
8. 写查询和测试：把 CQ 翻译为 SPARQL 或其他可执行检查。
9. 反复回现场验证：让业务人员确认语义、边界和例外。

这条路线的优点是严谨，缺点是慢。慢并不是因为知识工程师效率低，而是因为语义需要反复确认。军工领域尤其如此：一个词在不同型号、不同专业、不同阶段可能含义不同，不能靠建模人员猜。

所以，AI 出现之前，本体工程的关键瓶颈是“语义采集和验证成本高”。FDE 的价值正是在这里：把工程师放到真实工作流里，用现场反馈加快从粗糙道路到标准产品能力的迭代。

## 5. 有了 AI 后，本体论发生了什么变化

AI 没有让本体论过时，反而让本体论更重要。

原因很直接：LLM 擅长语言、归纳和生成，但不天然保证事实准确、规则一致和审计可复现。如果没有本体层，模型看到的是文档、表、接口和碎片上下文；它能组织出流畅回答，却很难保证每次都按同一套业务规则行动。

AI 给本体工程带来的真正变化，是加速外围劳动，而不是替代正确性底座：

| 过去人工做 | AI 可以加速 | 仍必须人工或系统确认 |
| --- | --- | --- |
| 从访谈纪要提 CQ | 初步抽取问题、分类、去重 | CQ 是否代表真实业务验收 |
| 从文档抽术语 | 生成候选术语和同义词 | 哪个术语是企业统一口径 |
| 从表结构猜对象 | 提出对象、属性、关系候选 | 是否符合业务对象边界 |
| 写 SPARQL 初稿 | 生成查询和测试草案 | 查询是否可执行、结果是否符合预期 |
| 写解释文本 | 把 evidence 讲成人话 | evidence 是否来自权威数据和确定规则 |

Palantir 的 AI FDE 正好体现了这种变化：AI FDE 可以用自然语言操作 Foundry，做数据转换、代码仓库、本体编辑、函数编辑等工作；但官方文档也强调它受用户权限、工具范围、审批、审计和分支机制约束。也就是说，AI 被放进了工程闭环里，而不是被放在正确性链路的最顶端。

对本项目来说，这个原则已经落实：

- LLM 不直接判定测量是否合格。
- QA 模块只接受白名单问题。
- 查询基于固定模板或结构化 evidence。
- 本地 fallback 可以在没有 LLM 时解释结果。
- CQ 把业务问题、SPARQL、预期结果和 evidence 字段绑定成验收契约。

这套分工特别适合军工企业。AI 可以帮助整理需求、生成草案、解释结果、辅助建模，但最终的事实、规则、权限、版本和审计必须在系统里。

## 6. 围绕 CQ 的后续方向

你给的截图把后续路线讲得很清楚：先做 CQ 工厂，再做骨架提取，再做验证闭环，最后用业务事件驱动扩展。这个方向非常适合作为本项目下一阶段叙事。

### 阶段一：CQ 工厂

输入来自利益相关人访谈、现有系统文档、报表、数据字典、界面截图和领域词汇草稿。输出不是本体，而是 CQ 注册表、完备性压测报告和术语候选列表。

这一阶段的要点是：CQ 是产出，不是随手输入。每个 CQ 都应该至少包含：

- 来源：来自哪次访谈、哪个系统、哪份规范、哪个报表。
- 优先级：是否影响核心业务判定。
- 类型：实例查询、关系查询、聚合统计、推理判断。
- 验收标准：预期能查到什么字段、什么结果算通过。

本项目现有 `docs/cq/measurement-judgement-cqs.md` 已经是第一批 CQ：`M007 为什么 Fail？`、`M008 为什么 Fail？`、`M009 为什么 Pass？`。下一步可以把它扩展为“试验判定 CQ 注册表”，再扩展到规格变更影响、批次汇总、参数扩展、异常复核等问题。

### 阶段二：骨架提取

这一阶段从 CQ 反推 TBox、RBox、ABox 门禁。

例如 CQ 问“某条测量为什么 Fail”，系统就必须有：

- `Measurement`
- `Parameter`
- `Specification`
- `Result`
- `Measurement -> Result`
- `Result -> Specification`
- `measuredValue`
- `lowerLimit`
- `upperLimit`
- `appliedRule`
- `againstSpecVersion`

也就是说，CQ 不是写在系统最后的测试用例，而是本体骨架的来源。凡是无法追溯到 CQ 的属性和关系，早期都应谨慎加入，否则很容易把本体建成“大而全字段仓库”。

### 阶段三：验证闭环

这一阶段把 CQ 翻译为 SPARQL 回归测试套件，并用样本 ABox 数据执行。失败要分类：

- 空集：模型或数据没有覆盖到问题。
- 不完整：字段缺失或关系路径不够。
- 误报：规则或查询口径错误。
- 超时：模型路径或图结构不适合查询。

本项目已经有 CQ 解析和集成测试雏形。后续要补的是“失败驱动修模”：测试失败不是单纯修代码，而是判断应该修 TBox、RBox、ABox 数据、SPARQL 查询、推理配置，还是业务术语定义。

### 阶段四：业务驱动增量扩展

真正健康的本体不是一次建完，而是由业务事件驱动扩展。比如：

- 新试验类型来了，补 CQ，再补对象或关系。
- 新规格条款来了，补约束层或判定函数。
- 跨系统需求来了，对齐上层本体或接口对象。
- 合规要求来了，加入义务、禁止、审批、留痕等 deontic 约束。
- 性能问题出现，区分推理层、物化层和查询层。

这对应 Palantir 的“本体持续演进”路线，也适合国内军工企业。军工需求不是静态需求，本体也不应该是静态词典。每次扩展都必须有业务触发事件、CQ 溯源、变更日志和回归测试。

## 7. 回到国内军工企业：实际能解决什么

如果把本项目的试验场景扩展到军工企业，本体优先应该解决以下问题。

第一，解决需求复用问题。不同型号的工艺验证、试验鉴定、质量放行逻辑相似，但参数和规范不同。本体可以把稳定结构沉淀下来，让新型号复用对象、关系、CQ 模板和判定框架，而不是复制一套系统。

第二，解决数据准确性问题。准确性不只是数值对不对，还包括单位、版本、来源、适用范围、判定规则、责任人和时间是否明确。本体通过属性定义、规格版本、约束和 evidence 链，把“这个数据为什么可信”结构化表达出来。

第三，解决跨系统语义一致问题。PLM 里的部件、MES 里的工序、QMS 里的质量问题、试验系统里的测量记录，不能只靠字段映射。需要一层共同对象模型说明它们在业务世界中的关系。

第四，解决变更影响分析问题。设计更改、材料替代、供应商变化、工艺窗口调整、验收准则变化，都会影响已有数据和结论。本体化以后，系统可以沿对象关系和规则版本计算影响范围。

第五，解决审计和可解释问题。军工质量体系里，结论必须能追溯到依据。本项目的 `Result` 不是一个孤立状态，而是保存了规则、规格版本、上下限、偏差、推理器和时间。这比“系统显示不合格”更接近可审计系统。

第六，解决 AI 可控落地问题。企业可以让 AI 读需求、抽 CQ、生成 SPARQL、解释 evidence，但不能让 AI 在没有约束的情况下直接改状态、下结论、放行产品。正确路径是：AI 面向本体对象和受控动作工作，最终由确定性规则、权限、审批和审计兜底。

## 8. 本项目后续可以怎么讲

对外讲这个项目时，不建议把重点放在“我们用了 OWL、Fuseki、Pellet、LLM”。这些是技术选型，不是价值主线。

更好的讲法是：

> 我们从制造业试验数据管理这个小场景切入，验证本体如何把动态参数、规格版本、判定规则、历史重算和推理解释统一起来。这个闭环可以扩展到军工企业中大量重复、相似、多变的需求场景，成为数据准确性、业务规则复用和 AI 可信落地的基础。

可以按三层来讲：

1. 对业务人员：它解决“为什么这样判、依据是什么、变更影响谁”的问题。
2. 对管理者：它把专家经验、规则口径和质量证据沉淀为组织资产。
3. 对技术人员：它用本体、图数据库、确定性规则、CQ 测试和受控 QA 组成可演进架构。

最后再回到一句朴素的话：

> 本体的价值不是把数据画成图，而是让企业在需求变化、规则变化、数据变化时，仍然能保证业务含义准确、判定依据准确、系统行为准确。
