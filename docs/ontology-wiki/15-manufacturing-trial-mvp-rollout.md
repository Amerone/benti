# 15 Manufacturing Trial MVP Rollout

## 先看结论

这份 `manufacturing-trial-ontology-mvp.docx` 真正要落地的，不是一个“大而全制造业本体平台”，而是一个可演示、可验证、可审计的最小闭环：

> 围绕“制造业试验数据管理”这个单一场景，证明本体路线在规格变更重判、参数动态扩展、推理链可解释三个问题上，存在传统系统很难替代的结构性优势。

按本 wiki 和现有 skills 的原则，这个项目应该这样推进：

1. 先做一个高价值、边界清晰的 MVP，不做企业总本体
2. 先把对象、关系、规格、规则和推理链建清楚，再谈 UI 和 Agent
3. 高风险判断走确定性规则，不让 LLM 直接承担最终判定
4. 先验证闭环，再决定是否扩到 MES、QMS、ERP 等更大范围

如果资源正常，这个项目适合按：

- `1 名工程师`
- `1 名工艺工程师 / 业务 owner`
- `1 名质量主管`
- `3 周`

完成一个可演示 MVP。

## 这份 docx 要解决什么问题

文档里的业务场景是：

- 制造业 NPI 阶段
- 针对试制批次做工艺验证
- 核心对象包括 `Trial`、`Batch`、`Measurement`、`Specification`、`Result`
- 核心动作是记录试验数据、执行判定、规格变更后重推理、对异常做解释

它聚焦的 3 个命题很清楚：

1. 规格变更后，历史结论能否自动重算
2. 试验过程中，能否动态新增参数而不改数据库表结构
3. 某条数据为什么失败，系统能否给出可审计的推理链

所以项目目标不应该写成：

- 建本体平台
- 建智能制造大脑
- 打通全部生产系统

更准确的目标应该写成：

> 在制造业试验数据管理场景中，用最小本体闭环证明“规格版本化 + 受控判定 + 推理链持久化 + 动态参数注册”可以被稳定落地。

## MVP 边界怎么划

### 必须包含

- 1 个试验场景
- 3 个批次
- 1 个主参数
- 1 版初始规格和 1 次规格变更
- 自动判定逻辑
- 历史重推理
- 动态参数注册
- 自然语言问答查询推理链

### 明确不做

- 生产级权限体系
- 复杂设备接入
- Kafka / 流式架构
- 多租户
- 全量主数据治理
- 企业级前端框架
- 跨工厂部署

这一步非常关键。  
如果一开始把边界放大，这个项目会从“验证本体路线”退化成“补一套制造执行平台”。

## 推荐的落地架构

结合 docx 内容和本 wiki 的严谨架构原则，推荐用下面这版：

```text
工艺工程师 / 质量主管 / 演示用户
                │
                ▼
Streamlit 演示界面
  ├─ 数据录入
  ├─ 规格变更重推理
  ├─ 新增参数
  └─ 推理链问答
                │
                ▼
FastAPI 应用层
  ├─ Trial / Batch / Measurement API
  ├─ ParameterRegistration API
  ├─ SpecChange API
  └─ QA API
                │
      ┌─────────┼─────────┐
      ▼         ▼         ▼
Ontology     Deterministic  LLM QA
Store        Inference      Claude
Fuseki       Python rules   只做查询解释
                │
                ▼
推理结果、规格版本、推理链持久化
```

这版架构里最重要的 4 个原则：

1. `Ontology` 负责统一对象、关系、规格和上下文
2. 最终判定逻辑先放在 `Python` 确定性模块里，不在 MVP 阶段依赖复杂推理引擎
3. `LLM` 只负责把查询结果翻译成自然语言解释，不直接产出最终业务结论
4. 所有结论都要回写推理链，包括规则名、规格版本、偏差值和时间戳

## 为什么这样落地，而不是完全照文档字面实现

docx 里给了：

- Protégé
- Fuseki
- Owlready2 + Pellet
- FastAPI
- Streamlit
- Claude API

这个方向是对的，但真正落地时要做一点收敛：

### 1. MVP 阶段把最终判定放在 Python

这是对的，应该保留。

原因不是“本体没用”，而是：

- 可解释性更强
- 调试更快
- 演示更稳
- 规则变更更可控

也就是说：

- 本体负责表达对象、关系、规格版本和上下文
- Python 负责执行确定性判定
- LLM 负责说明“为什么这样判”

### 2. 动态参数注册不要直接理解成“任意开放世界”

更稳的做法是：

- 允许运行时注册新参数
- 但参数元数据必须最少包含：名称、单位、类型、适用 Trial、上下限来源、是否参与判定

否则它会从“参数扩展能力”退化成“任意塞字段”。

### 3. 问答能力必须受控

问答模块不能做成自由问答。

建议只支持三类问题：

- 某条测量为何 Fail / Pass
- 某次规格变更影响了哪些数据
- 某参数 / 批次 / 试验的统计摘要是什么

这样才能保证演示稳定，也更符合本 wiki 里“工具要窄、结果要结构化”的原则。

## 代码和模块怎么拆

docx 里的目录结构基本合理，可以直接采用，但建议把职责再说清楚：

### `ontology/manufacturing-trial.ttl`

负责：

- 类定义
- 属性定义
- 对象关系
- 规格版本关系
- 推理链字段定义

不负责：

- 复杂运行时业务逻辑
- UI 规则

### `core/graph.py`

负责：

- 对 Fuseki 的查询和写回封装
- 参数注册
- 测量值写入
- 推理结果回写

### `core/inference.py`

负责：

- 单条数据判定
- 规格变更后的批量重推理
- 生成差异报告

这是 MVP 的业务核心。

### `core/parameters.py`

负责：

- 参数元数据注册
- 参数校验
- 参数查询

建议把参数注册从 `graph.py` 中拆出来，避免图存储逻辑和参数域逻辑混在一起。

### `core/qa.py`

负责：

- 受控问题模板
- SPARQL 查询生成
- 查询结果转中文解释

### `api/main.py`

负责：

- 对外 REST 端点
- 参数校验
- 把用例调到对应模块

### `app.py`

负责：

- 演示交互
- 不承载业务规则
- 不直接写 SPARQL

## 推进顺序怎么排

按照渐进式披露和最小闭环原则，不要先搭前端，也不要先做问答。

更合理的推进顺序是：

### Phase 0：确认试点边界

先确认 5 件事：

1. 只做一个试验场景
2. 三个命题就是验收范围，不再额外加需求
3. 有一份可演示的样例数据
4. 有工艺工程师确认规格和规则
5. 有质量主管确认放行口径

没有这一步，后面会不断漂移。

### Phase 1：先建最小本体

先在 Protégé 里完成：

- `Trial`
- `Batch`
- `Parameter`
- `Measurement`
- `Specification`
- `Result`

以及关键关系：

- `Trial -> Batch`
- `Batch -> Measurement`
- `Measurement -> Parameter`
- `Measurement -> Specification`
- `Measurement -> Result`

这一阶段的产物不是“图能跑”，而是“业务对象和版本关系能讲清楚”。

### Phase 2：打通图存储和基础读写

目标只有两个：

- 能写入测量值
- 能查询上下文

这一步不要急着做推理。

### Phase 3：实现确定性判定与推理链持久化

这是 MVP 最重要的一步。

至少要把每次判定写成结构化结果：

- `measurement_id`
- `result`
- `rule_name`
- `spec_version`
- `upper_bound`
- `lower_bound`
- `deviation`
- `evaluated_at`

有了这一步，规格变更重推理和问答才有基础。

### Phase 4：实现规格变更重推理

这一步是第一命题的核心。

需要交付：

- 新旧规格版本关系
- 历史测量批量重推理
- 差异清单
- 受影响批次统计

### Phase 5：实现参数动态注册

这一步是第二命题的核心。

建议最小注册字段：

- 参数编码
- 参数名称
- 单位
- 值类型
- 适用试验
- 是否参与判定

### Phase 6：最后再接问答和演示 UI

这是最后做，不是最先做。

因为只有前面的对象、规则、推理链都稳定了，问答才不会变成“模型自由发挥”。

## 三周推进建议

### 第 1 周：把语义和底层打稳

- Day 1：确认业务边界、对象、规则和演示命题
- Day 2：完成本体建模初版
- Day 3：部署 Fuseki，验证读写链路
- Day 4：落 `graph.py`
- Day 5：落单条判定逻辑

第 1 周结束时必须达到：

- 能录入数据
- 能执行单条判定
- 能回写结构化推理结果

### 第 2 周：把两个硬命题做出来

- Day 1：规格版本模型和变更接口
- Day 2：历史重推理
- Day 3：差异报告
- Day 4：参数动态注册
- Day 5：联调和补数据

第 2 周结束时必须达到：

- 规格变更后能自动重推理
- 新参数能注册并出现在录入界面

### 第 3 周：把演示和解释做稳

- Day 1：受控问答模块
- Day 2：Streamlit 四个 Tab
- Day 3：演示脚本、演示数据、异常案例
- Day 4：对比材料整理
- Day 5：缓冲和打磨

第 3 周结束时必须达到：

- 三个命题都能现场稳定演示
- 每个命题都有对比说明

## 谁来推进，谁来拍板

建议角色分工如下：

- 工艺工程师  
  负责定义试验对象、参数、规格和规则

- 质量主管  
  负责确认异常判定口径和放行逻辑

- 工程师  
  负责本体、API、推理、UI 和问答整合

- 业务 sponsor  
  负责守住范围，不让项目在 3 周内膨胀

最容易失败的原因不是技术，而是业务口径没有人拍板。

## 演示应该怎么讲

不要从“我们用了 OWL、Fuseki、Claude”开始讲。

更好的演示顺序是：

### 演示 1：先录一条超标数据

让系统直接给出：

- Fail
- 使用的规格版本
- 命中的规则
- 偏差值

### 演示 2：再改规格上限

展示：

- 历史哪些数据结论变了
- 哪些批次受影响
- 旧版本和新版本都保留

### 演示 3：再新增一个参数

展示：

- 无需改表
- 无需重启
- 界面立即可录入

### 演示 4：最后问“为什么 M007 Fail”

展示：

- 不是只返回结论
- 而是返回完整推理链

这样讲，业务方能直接看到它和传统系统的差异。

## 验收标准怎么定

直接沿用 docx 的三个命题，但建议补成更工程化的验收口径：

### 命题一：规格变更历史自动重算

验收标准：

- 在一次规格变更后，系统能自动重推理全部历史样例
- 输出差异报告
- 全程不靠人工逐条重判

### 命题二：新增参数无需改代码

验收标准：

- 注册新参数后，无需改数据库 schema
- 无需重启服务
- 录入界面立即可用

### 命题三：推理链自然语言可查

验收标准：

- 对一条失败记录提问时
- 系统回答必须精确到测量值、规格版本、规则名、偏差值
- 回答内容来自图谱中的结构化证据，不是模型臆测

## 项目最容易跑偏的地方

### 1. 一开始就想接真实产线设备

这会把试点从“验证语义闭环”拖进“工业集成项目”。

### 2. 一开始就想做全量制造本体

这会把试点从“单场景验证”拖进“企业大模型建模工程”。

### 3. 把 LLM 当最终判定引擎

这会直接破坏可审计性。

### 4. 把动态参数注册做成任意字段注入

这会让模型边界迅速失控。

### 5. 先做漂亮 UI，再补业务规则

这会导致演示看起来顺，但核心命题没有被证明。

## MVP 之后怎么扩

如果三个命题验证通过，下一步不要立刻“全面推广”，更合理的是：

1. 扩第二个试验场景  
   验证对象和规则是否可复用

2. 接真实系统中的一个只读数据源  
   比如 MES 或 QMS

3. 增加人工 Override 决策节点  
   把“人工例外决策”也写成图谱对象

4. 再决定是否把 Python 判定逻辑逐步迁到更正式的规则层

## 这一页应该记住什么

1. 这个项目不是要做制造业总本体，而是验证一个最小业务闭环。
2. 三个核心命题就是项目边界，不要在 MVP 阶段继续扩范围。
3. 本体负责表达对象和上下文，确定性代码负责判定，LLM 负责解释。
4. 先把推理链持久化，再做规格变更和问答，否则系统不可审计。
5. 真正的推进顺序应该是“对象和规则 -> 图读写 -> 判定 -> 重推理 -> 参数扩展 -> 问答和 UI”。
