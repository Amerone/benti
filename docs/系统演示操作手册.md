# 制造业试验数据管理本体 MVP 演示操作手册

本文用于现场演示本系统。目标不是从零讲完全部技术细节，而是让演示者能稳定地把系统跑起来，并按一条清晰业务故事展示：

1. 本体如何作为业务语义底座。
2. 试验数据如何写入图数据库。
3. 测量值如何被确定性规则判定。
4. 规格变更后历史数据如何重算。
5. 系统如何解释“为什么 Pass / Fail”。
6. CQ 如何把业务问题变成可执行验收资产。

## 1. 演示前准备

### 1.1 演示环境

推荐环境：

| 项目 | 推荐值 |
| --- | --- |
| 操作系统 | Windows + PowerShell |
| Python | 3.11+ |
| 图数据库 | Apache Jena Fuseki |
| 后端 | FastAPI / Uvicorn |
| 前端 | Streamlit |
| 浏览器 | Chrome / Edge |

默认端口：

| 服务 | 地址 |
| --- | --- |
| Fuseki | `http://localhost:3030` |
| API | `http://127.0.0.1:8000` |
| 前端 | `http://127.0.0.1:8501` |

### 1.2 演示前检查清单

演示前建议逐项确认：

- `python -m pytest -q` 能通过，允许外部依赖相关测试 skip。
- `docker compose up -d` 能启动 Fuseki，或本机已有可写 Fuseki。
- `.env` 中的 `FUSEKI_BASE_URL`、`FUSEKI_DATASET`、`FUSEKI_USER`、`FUSEKI_PASSWORD` 正确。
- 后端健康检查 `http://127.0.0.1:8000/api/v1/health` 可访问。
- 前端 `http://127.0.0.1:8501` 可访问。
- 已经导入或准备导入演示数据。

如果本机 3030 端口已被别的 Fuseki 占用，先确认它是否就是本次演示要用的服务。不要误停其它项目正在使用的容器。

## 3. 推荐演示讲解主线

建议用下面这条主线讲，不要一上来讲 RDF / OWL / SPARQL 术语。

### 3.1 开场话术

可以这样介绍：

> 这个系统演示的是制造业试验数据管理中的一个最小闭环：记录试验测量值，根据规格上下限做判定，规格变化后自动重算历史结果，并能解释某条数据为什么 Pass 或 Fail。

再补一句：

> 本体在这里不是抽象概念，而是系统统一理解 Trial、Batch、Measurement、Specification、Result 这些业务对象的语义底座。

## 4. 页面演示步骤

### 4.1 第一步：本体页签

进入 `本体` 页签。

操作：

1. 在“切换当前本体”中选择 `manufacturing-trial`。
2. 点击“重新装载本体”。
3. 查看“已发现本体”表格。

讲解重点：

- 本体定义了这个系统里有哪些业务对象。
- 本体加载后会写入 Fuseki 的 ontology graph。
- 这里不是直接写业务测量数据，而是先把“业务世界的结构”加载进去。

预期现象：

- 页面提示“本体装载已完成”。
- 表格中 `manufacturing-trial` 显示 loaded。
- trace 面板能看到本体加载步骤。

如果失败：

- 检查 Fuseki 是否启动。
- 检查 `.env` 里的账号密码。
- 如果是 `401`，说明 Fuseki 写入需要认证。

### 4.2 第二步：主体页签

进入 `主体` 页签。

操作：

1. 名称过滤可以先留空。
2. 返回上限保持默认。
3. 点击“刷新主体”。
4. 依次查看 `类`、`个体`、`对象属性`、`数据属性`。

讲解重点：

- `类` 是业务对象类型，例如 `Trial`、`Batch`、`Measurement`、`Specification`、`Result`。
- `个体` 是具体业务对象，例如某次试验、某条测量。
- 属性说明对象之间怎么关联、对象有哪些字段。

推荐现场指出：

```text
Measurement 表示测量值。
Specification 表示规格版本。
Result 表示判定结果。
```

预期现象：

- 表格里能看到本体类和属性。
- 页面下方 trace 能显示主体读取链路。

### 4.3 第三步：推理页签

进入 `推理` 页签。

操作：

1. 可保持“强制重跑”为关闭。
2. 点击“执行 Pellet”。
3. 查看 `Pellet 状态`、`耗时 ms`、`新增推断`。

讲解重点：

- Pellet 用于本体推理和 SWRL 对照。
- 本系统的主业务判定不依赖 LLM，也不强依赖 Pellet。
- 主判定链路是 Python 确定性规则，Pellet 主要作为本体推理和对照能力。

预期现象：

- `Pellet 状态` 返回 `success` 最理想。
- 如果显示 `failed` 或 `missing_java`，可以说明本项目仍能走确定性判定主线。

兜底话术：

> Pellet 是增强推理链路。即使它暂时不可用，测量判定和本地问答 fallback 仍可以演示，因为主业务判断由确定性规则完成。

### 4.4 第四步：测量页签，演示自动判定

进入 `测量` 页签。

#### 4.4.1 录入一条高温失败测量

在“录入测量值”区域填写：

| 字段 | 值 |
| --- | --- |
| `measurement_id` | `M007` |
| `batch` | `B03` |
| `parameter` | `temperature` |
| `value` | `197.2` |
| `operator` | `Streamlit` |

点击“提交测量”。

讲解重点：

- 当前 `temperature` 的 `Spec_v1` 是 `180 ~ 195`。
- `197.2` 高于上限 `195`。
- 系统应判定为 `Fail_High`。
- 同时保存规则名、规格版本、偏差和推理来源。

预期现象：

- 测量列表中出现 `M007`。
- `status` 是 `Fail_High`。
- `rule` 是 `Rule_Fail_High`。
- `deviation` 是 `2.2`。
- `source_badges` 中出现 `Python`。

#### 4.4.2 可选：打开 Pellet-SWRL 对照

如果现场环境 Pellet 可用，可以勾选：

```text
启用 Pellet-SWRL 对照模式
```

再提交一条测量，例如：

| 字段 | 值 |
| --- | --- |
| `measurement_id` | `M777` |
| `batch` | `B03` |
| `parameter` | `temperature` |
| `value` | `197.2` |

讲解重点：

- Python 确定性链路是主结论。
- Pellet-SWRL 对照链路用于验收和比对。
- 页面会展示来源徽标。

预期现象：

- 测量列表里来源可能出现 `Python / Pellet-SWRL`。

如果 Pellet 失败：

- 不要卡在这里。
- 直接说明对照链路依赖 Pellet，主链路仍可演示。

### 4.5 第五步：测量页签，演示规格变更影响

仍在 `测量` 页签。

在“规格变更与影响复核”区域填写：

| 字段 | 值 |
| --- | --- |
| `parameter` | `temperature` |
| `reason` | `产线收紧` |
| `lower` | `180` |
| `upper` | `190` |

点击“提交规格变更”。

讲解重点：

- 系统不会覆盖旧规格，而是创建新规格版本。
- 规格从 `180 ~ 195` 收紧到 `180 ~ 190`。
- 系统会重跑该参数历史测量。
- 受影响的数据会出现在差异报告里。

推荐讲解例子：

```text
原来 192.1 在 180 ~ 195 里是 Pass。
新规格上限变成 190 后，192.1 会变成 Fail_High。
```

预期现象：

- 页面出现差异报告。
- `new_spec` 变成新版本。
- `changed` 数量大于 0。
- 表格中能看到状态变化。

### 4.6 第六步：问答页签，演示运行时新增参数

进入 `问答` 页签。

在“运行时新增参数”区域填写：

| 字段 | 值 |
| --- | --- |
| `code` | `vibration_frequency` |
| `name` | `振动频率` |
| `unit` | `Hz` |
| `value_type` | `number` |
| `参与推理` | 开启 |

点击“注册参数”。

讲解重点：

- 系统支持运行时新增参数。
- 不需要改数据库表结构。
- 参数也是业务语义的一部分，会写入 data graph。

预期现象：

- 参数列表中出现 `vibration_frequency`。
- 如果重复注册，可能显示 `created=false` 或复用已有参数，这是正常的幂等行为。

### 4.7 第七步：问答页签，演示解释能力

仍在 `问答` 页签。

在“自然语言问答”区域输入：

```text
M007 为什么 Fail？
```

点击“提交问题”。

讲解重点：

- 问答不是让 LLM 自由判断。
- 系统先识别问题意图。
- 再读取图数据库中的结构化 evidence。
- 最后由 LLM 或本地 fallback 把 evidence 解释成人话。

预期现象：

- 页面显示解释文本。
- `source` 可能是 `local_fallback` 或具体 LLM provider。
- 展开“查看 SPARQL / Evidence”后，能看到：
  - SPARQL 查询。
  - `measurement_id`
  - `value`
  - `status`
  - `rule`
  - `spec_version`
  - `lower_limit`
  - `upper_limit`
  - `deviation`
  - `reasoner`
  - `inferred_at`

可以继续演示：

```text
M003 为什么 Pass？
```

或如果使用 CQ fixture：

```text
M009 为什么 Pass？
```

## 5. CQ 验收演示

CQ 是 competency question，也就是“胜任力问题”。在本系统中，CQ 的作用是把业务问题变成可执行验收。

### 5.1 先给观众解释 CQ

可以这样讲：

> 我们不是只写“系统应能解释失败原因”这种模糊需求，而是把需求变成具体问题，比如“M007 为什么 Fail？”。每个 CQ 都绑定 SPARQL、期望结果和 evidence 字段。只要 CQ 测试通过，就说明本体、数据、推理和问答链路一起跑通了。

### 5.2 运行 CQ 解析测试

```powershell
python -m pytest tests/test_cq_parser.py -q
```

预期现象：

```text
5 passed
```

讲解重点：

- 这一步验证 CQ Markdown 结构正确。
- 验证 graph IRI 占位符能按 ontology 渲染。

### 5.3 运行真实 Fuseki CQ 集成测试

如果 Fuseki 写入需要认证，先在当前 PowerShell 里设置环境变量，或确保 `.env` 已配置。

```powershell
$env:FUSEKI_TEST_TIMEOUT='30'
python -m pytest tests/test_cq_integration.py -q -rs
```

预期现象：

```text
1 passed
```

如果显示 skipped：

- `Fuseki unavailable`：Fuseki 没启动或 dataset 不对。
- `requires write credentials`：缺少 `FUSEKI_USER` / `FUSEKI_PASSWORD`。

讲解重点：

- CQ 集成测试会准备 CQ 专用 fixture。
- 会执行 SPARQL 查询。
- 会校验 Expected。
- 会走 QA 链路。
- 会校验 QA evidence 和 SPARQL 结果一致。

### 5.4 CQ 文件位置

```text
docs/cq/measurement-judgement-cqs.md
```

初学者说明：

```text
docs/cq/cq-beginner-guide.md
```

## 8. 委托单试验本体演示

这一段用于演示新的 `commission-testing` 本体：从委托单业务出发，自动分解试验任务，录入测试数据，发布新标准，并让系统自动找出历史结论翻转。

### 客户演示

1. 打开 `委托单试验` 页签。
2. 点击“初始化 CO-2024-001 演示剧本”。
3. 展示委托单、产品、两个试验项目和两个自动任务。
4. 点击“发布 V2 标准并重判历史数据”。
5. 展示 RCS 均值从 `Pass` 翻转为 `Fail`，任务 `T-001` 自动变为 `NeedsReview`。
6. 说明误码率阈值未变，所以 `T-002` 仍为 `Pass`。

客户讲解重点：

- 委托单、产品、试验项目、任务、测试项、数据、标准、判据和结果是显式语义网络。
- 标准升级后系统自动找出旧标准下的数据并重判。
- 结论翻转不会覆盖旧结果，而是形成可追溯影响记录。

### 开发演示

1. 打开 `技术讲 -> CQ 工程台`。
2. 选择 `llm_with_template_fallback` 或 `template_only`。
3. 点击“生成候选 CQ / TBox / RBox”。
4. 查看候选 CQ、类、关系、属性、规则和草案 JSON。
5. 打开 `docs/cq/commission-testing-cqs.md` 展示可执行 CQ。
6. 运行：

```powershell
python -m pytest tests/test_commission_cq_engine.py -q
python -m pytest tests/test_commission_cq_integration.py -q -rs
```

开发讲解重点：

- LLM 只生成候选草案，不直接覆盖正式 OWL。
- `template_only` 保证无网络或无 Key 时仍可演示。
- CQ SPARQL 是自动回归资产，不是普通问答样例。

## 10. 常见故障与处理

### 10.1 前端打不开

检查 Streamlit 是否启动：

```powershell
streamlit run mvp/frontend/app.py --server.port 8501
```

如果 8501 被占用：

```powershell
streamlit run mvp/frontend/app.py --server.port 8502
```

### 10.2 后端打不开

检查 API：

```powershell
Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8000/api/v1/health
```

如果失败，重新启动：

```powershell
uvicorn mvp.api.main:app --reload --host 0.0.0.0 --port 8000
```

### 10.3 Fuseki 写入 401

现象：

```text
FUSEKI_HTTP_401
```

处理：

- 检查 `.env` 里的 `FUSEKI_USER`。
- 检查 `.env` 里的 `FUSEKI_PASSWORD`。
- 确认启动后端的终端读取到了这些环境变量。

### 10.4 本体加载成功但主体为空

处理顺序：

1. 回到 `本体` 页签重新装载本体。
2. 确认当前本体是 `manufacturing-trial`。
3. 在 `主体` 页签点击“刷新主体”。
4. 检查后端日志是否有 TTL 解析或 Fuseki 查询错误。

### 10.5 测量列表没有参数

处理：

1. 先运行 `python -m mvp.demo_data`。
2. 或在 `问答` 页签注册参数。
3. 确认 `temperature` 参数存在。

### 10.6 提交测量后显示 `not_inferred`

常见原因：

- 参数没有设置为参与推理。
- 参数没有规格。

处理：

- 先注册参数并开启“参与推理”。
- 再创建或变更规格。
- 然后重新提交测量。

### 10.7 LLM 不可用

这不影响主线演示。

系统会使用 `local_fallback` 基于 evidence 生成解释。可以这样说明：

> 这里故意不依赖 LLM 做业务裁决。LLM 不可用时，系统仍可用本地 fallback 解释结构化证据。

### 10.8 Pellet 不可用

这不影响主线测量判定。

可以这样说明：

> Pellet 是本体推理和 SWRL 对照链路。主业务判断由 Python 确定性规则完成，所以 Pellet 不可用时，Pass/Fail 主流程仍然可以演示。

## 11. 演示成功标准

一次完整演示至少应证明：

- 本体能被加载。
- 主体页能看到类、个体和属性。
- 测量值能写入。
- 系统能给出 `Pass / Fail_Low / Fail_High`。
- 规格变更后能产生影响报告。
- 问答能解释结果，并能展示 evidence。
- CQ 测试能证明业务问题可执行验收。
