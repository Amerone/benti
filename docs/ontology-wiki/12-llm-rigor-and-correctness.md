# 12 LLM Rigor And Correctness

## 先说最重要的一句

LLM 本身不是正确性引擎。

它本质上是概率模型，擅长：

- 理解意图
- 组织表达
- 做归纳
- 规划调用

但它不应该被当成：

- 最终事实来源
- 最终规则执行器
- 最终金额计算器
- 最终高风险写操作裁决者

所以如果你的场景对数据严谨性要求高，真正要做的不是“相信模型更聪明”，而是：

> 把正确性尽量从模型内部拿出来，放到数据源、工具契约、规则层、校验层和受控流程里。

## 先回答你的核心问题

### MCP、Skills、Tool Calling 能不能保证正确性

不能直接保证。

它们只是帮助你：

- 连到外部系统
- 暴露能力
- 约束执行流程

真正保证正确性的，不是“接了 MCP”或者“用了 Skills”，而是下面这些机制有没有到位：

- 数据是否来自权威源
- 工具接口是否窄而明确
- 返回结果是否结构化且可校验
- 关键规则是否由确定性逻辑执行
- 高风险动作是否走审批 / workflow
- 结果是否可追溯、可重放、可审计

所以要先建立一个正确认识：

> MCP / Skills 是正确性体系里的连接层和执行层，不是正确性本身。

## 高严谨场景里，LLM 应该负责什么

最稳的做法是让 LLM 主要负责 4 类事情：

### 1. 意图理解

例如把用户的话识别成：

- 查询哪个对象
- 需要哪种时间范围
- 需要什么粒度

### 2. 查询规划

例如决定：

- 先查订单
- 再查库存
- 再查客户约束
- 最后调用资格判定函数

### 3. 结果解释

把结构化结果翻译成人能看懂的话。

### 4. 参数收集

当输入不完整时，向用户追问缺失参数。

这 4 件事都很适合 LLM。

## 高严谨场景里，LLM 不应该直接负责什么

### 1. 不应该直接生成事实

例如：

- 订单金额是多少
- 当前库存是多少
- 哪笔交易异常

这些必须来自权威数据源或受控工具。

### 2. 不应该直接执行关键规则

例如：

- 授信是否通过
- 是否允许放行
- 是否满足合规要求

这类判断应该由：

- 规则引擎
- 本体函数
- 确定性服务
- SQL / 代码 / policy engine

执行。

### 3. 不应该直接拼写高风险写操作

例如：

- 改状态
- 放款
- 批准
- 删除

这些必须走受控 action / workflow。

### 4. 不应该单独承担审计责任

模型说“我判断是这样”不构成审计依据。

审计依据必须是：

- 数据快照
- 规则版本
- 动作记录
- 工具调用日志

## 一个最稳的分工公式

在严谨数据场景里，建议记住这个分工：

> LLM 负责“理解、规划、解释”，工具负责“取数、计算、校验、执行”。

如果再进一步压缩：

- 模型管语言
- 系统管事实
- 规则层管正确
- 流程层管风险

## 如何设计 MCP / Skills 才更严谨

不是所有工具暴露方式都一样安全。

## 原则一：工具要窄，不要泛

不推荐直接暴露：

- 任意 SQL 执行
- 任意 shell
- 任意写接口

更推荐暴露：

- `get_order_by_id(order_id)`
- `get_inventory_position(sku, warehouse_id)`
- `evaluate_expedite_eligibility(order_id)`
- `request_expedite(order_id, reason)`

也就是：

> 给 LLM 的不是“自由发挥接口”，而是“业务能力接口”。

这样做的好处是：

- 语义更稳定
- 参数更明确
- 风险更可控
- 更容易测试

## 原则二：工具返回必须结构化

不要让工具主要返回一大段自然语言。

更好的返回方式是：

- JSON
- 明确字段
- 明确类型
- 明确单位
- 明确时间戳
- 明确来源 ID

例如：

```json
{
  "order_id": "O-1024",
  "eligible": false,
  "reasons": [
    "inventory_shortage",
    "customer_tier_not_eligible"
  ],
  "source_snapshot_time": "2026-04-17T10:32:11+08:00",
  "rule_version": "expedite-eligibility-v3"
}
```

这比一段“看起来合理”的自然语言强很多。

## 原则三：工具接口要带业务语义，不只带技术参数

比如不要只给：

- `table_name`
- `column_name`
- `filter`

而要尽量给：

- `order_id`
- `customer_id`
- `shipment_id`
- `rule_version`

这样做的意义在于：

- 模型更不容易乱拼查询
- 工具更容易校验
- 审计更容易回放

## 原则四：读写分离

高严谨场景中，读工具和写工具要强分离。

例如：

- 读工具：查对象、查规则结果、查证据
- 写工具：发起审批、提交动作、确认执行

不要让同一个“万能工具”既能查也能随便改。

## 原则五：写工具必须做幂等和权限校验

对于关键动作，至少要有：

- 权限校验
- 参数校验
- 业务前置条件校验
- 幂等键
- 审计日志

否则模型一次重复调用，就可能造成真实事故。

## 如何保证“数据正确”，而不是“回答像真的”

如果你要真正追求严谨，建议按下面 8 层做。

## 第一层：权威数据源

所有关键事实都必须来自：

- 生产库只读视图
- 可信数仓快照
- 受控 API
- 经过治理的对象层

不能来自：

- Prompt 里的假设
- 文档里的样例
- 模型自己补出来的值

## 第二层：结构化契约

所有工具输入输出都要有契约。

常见做法：

- JSON Schema
- Pydantic
- TypeScript types
- OpenAPI

没有契约，模型就会“猜字段”。

## 第三层：确定性规则执行

凡是高风险判断，尽量不要让模型直接做最终裁决。

更好的做法是让模型调用：

- `evaluate_credit_eligibility()`
- `validate_release_conditions()`
- `compute_pricing_delta()`

这些函数内部用确定性规则执行。

## 第四层：多重校验

关键结果至少做一层以上校验。

例如：

- 金额总和校验
- 主键存在性校验
- 状态合法性校验
- 时间窗口校验
- 跨源一致性校验

如果系统能在返回给用户前自动校验一遍，可靠性会明显提升。

## 第五层：证据回传

LLM 最终不只返回结论，还要返回证据。

至少包括：

- 数据来源
- 关键对象 ID
- 时间戳
- 命中的规则
- 规则版本

这样用户看到的不只是“答案”，而是“答案从哪来”。

## 第六层：高风险动作双阶段执行

推荐模式是：

1. 模型先生成动作提案
2. 系统做校验
3. 人工或 workflow 审批
4. 再执行动作

不要让模型一句话直接落库。

## 第七层：审计与可回放

每次关键调用都建议记录：

- 用户输入
- 模型输出
- 工具调用序列
- 工具返回值
- 使用的规则版本
- 最终动作结果

这样出了问题才有能力复盘。

## 第八层：离线评测与在线监控

严谨场景一定要做 eval。

至少包括：

- 典型样本集
- 边界条件样本
- 错误注入样本
- 回归测试集

上线后还要监控：

- 工具调用失败率
- 人工接管率
- 错判率
- 重试率

## 在本体场景里，怎么把严谨性做进去

如果你已经采用了本体 / operational ontology，这件事会更容易，因为你可以把正确性分散到几个稳定位置上。

### 1. 对象层负责统一事实入口

例如：

- `Order`
- `Shipment`
- `Customer`

这样模型不需要直接猜底层表。

### 2. 关系层负责上下文闭环

模型可以沿关系拿到：

- 订单对应客户
- 订单对应库存
- 订单对应履约状态

而不是自己拼跨表语义。

### 3. 函数层负责确定性判断

例如：

- `isEligibleForExpedite(order_id)`
- `isReleaseAllowed(work_order_id)`

这类逻辑不交给 LLM 自由判断。

### 4. 动作层负责受控写操作

例如：

- `RequestExpedite`
- `ApproveRelease`

模型只能发起动作，不能随便改字段。

### 5. 对象视图负责把证据展示给人

这会让：

- 业务人员
- 审批人
- 审计人员

都能看到判定依据。

## 一个推荐的调用模式

可以把高严谨场景的调用模式设计成下面这样：

```text
用户问题
  ↓
LLM 做意图解析
  ↓
调用对象查询工具
  ↓
调用确定性规则函数
  ↓
系统做结构化校验
  ↓
LLM 只负责把结构化结果解释给用户
  ↓
如需写操作，进入 workflow / 审批
  ↓
执行受控 action
```

这个模式的重点是：

- 结论不是模型脑补出来的
- 模型只是编排和解释

## 一个反例

下面这种方式风险很高：

```text
用户问：这笔订单能不能加急？
  ↓
LLM 读几段文档
  ↓
LLM 自己猜规则
  ↓
LLM 自己查几个表
  ↓
LLM 直接调用写接口改状态
```

这类方案的问题是：

- 规则不稳定
- 证据不完整
- 审计困难
- 很难兜底

## 真正的“保证正确性”应该怎么理解

在工程上，不要追求一种不现实的说法：

- “100% 保证模型永不犯错”

更现实的目标应该是：

> 即使模型会犯错，系统也能把错误限制在可发现、可回退、可审计、可控的范围里。

这才是严谨系统真正应该追求的。

## 一个实用清单

如果你要检查一个 LLM + MCP / Skills 系统是否足够严谨，可以直接看下面这张清单。

### 数据面

- 是否只从权威源取关键事实
- 是否返回结构化数据
- 是否带来源和时间戳

### 规则面

- 关键规则是否由确定性逻辑执行
- 是否有版本号
- 是否能解释命中了哪条规则

### 工具面

- 是否是窄接口而不是万能接口
- 是否读写分离
- 是否有参数校验和权限控制

### 流程面

- 高风险动作是否双阶段执行
- 是否有人审 / workflow
- 是否能回滚

### 监控面

- 是否记录工具调用链
- 是否有回归测试
- 是否监控人工接管和错判

## 这一页应该记住什么

只记住 6 句：

1. LLM 不能直接保证严谨数据场景的正确性。
2. MCP / Skills 只是连接层和执行层，不是正确性本身。
3. 正确性要来自权威数据源、结构化契约、确定性规则、校验和 workflow。
4. LLM 最适合做意图理解、调用规划、解释和参数收集。
5. 高风险判断和写操作必须尽量从模型里拿出来。
6. 真正可靠的系统，不是模型永不出错，而是错误被限制在可控边界内。
